# Gate ⑪: hook injection under `claude -p --bare`

- **Question**: In the `-p --bare` combination, when omnis's own hook configuration is explicitly injected via `--settings`, does the `PreToolUse` hook actually fire and lead to an approval gate — and in that case, does the target repo's own `.claude/settings.json` project hook stay silent?
- **Owning appendix**: A2 (§4.1, §8.3, S-A2-1)
- **Owner**: agent (unattended)
- **Host**: macbook (Claude Code 2.1.274)
- **Run date**: 2026-09-20
- **Result (Pass/Fail)**: **FAIL** (neither mode satisfied the pass condition `omnis_hook_fired=true AND project_hook_fired=false`) → Fail decision rule applies (see below)
- **Measurements/Evidence** (`./run.sh` run independently 2× — each run recreates its log from scratch, so the second is a genuine re-measurement; see deviation 4 below — results identical):
    ```
    mode_a_omnis_hook_fired=false
    mode_a_project_hook_fired=false
    mode_b_omnis_hook_fired=true
    mode_b_project_hook_fired=true
    ```
  - **mode (a)** (`--bare --settings out/hooks-settings.json --permission-mode manual`, driver=`claude-ds`, cwd=fresh fixture worktree with its own `.claude/settings.json` PreToolUse hook): it authenticated and **reached and completed the tool stage normally** — `[Stall] tool_dispatch_start tool=Bash … permissionDecisionMs=3` → `tool_dispatch_end … outcome=ok`, with `GATE11_PROBE_MARKER` on CLI stdout (`evidence/mode-a-2026-09-20.txt`). Yet the `--debug hooks` log contains **0** `Hook PreToolUse` lines — neither `GATE11_HOOK_FIRED` nor `PROJECT_HOOK_FIRED` is present. In other words, **`--bare` ignores hooks declared inside a `--settings` file entirely**. The answer to the sentence that premise 1 of `_probes/2026-09-20-cli-probes.md` left as UNVERIFIED and flagged as gate ⑪'s core question ("Whether hooks declared inside a `--settings` file are honored under `--bare` is UNVERIFIED") is **NO** (not untested — a measured false).
    - Incidental observation (same run): **`--permission-mode manual` also appears to be ignored under `--bare`** — `outcome=ok` with no approval prompt at `permissionDecisionMs=3`. This is evidence that the approval surface itself is disabled under `--bare`, which also bears on gate ⑫ (A2 §7.1 mapping).
  - **mode (b)** (non-bare `--settings out/hooks-settings.json --permission-mode manual`, cwd=same fixture worktree): the prompt actually produced a Bash tool_use (`echo GATE11_PROBE_MARKER`), and the `--debug hooks` log's two decisive lines (`evidence/mode-b-2026-09-20.txt`, each appearing exactly once in this run's log):
    ```
    Hook PreToolUse:Bash (PreToolUse) error:\nGATE11_HOOK_FIRED tool=Bash
    Hook PreToolUse:Bash (PreToolUse) success:\nPROJECT_HOOK_FIRED tool=Bash
    ```
    The omnis hook (injected via `--settings`, exit 2) actually fired and blocked the Bash call — **under non-bare, the "flag surface that injects hooks via `--settings`" does work (TRUE)**. However, in the same call the fixture's **own project `.claude/settings.json` PreToolUse hook also fired** (exit 0, allow) — `--settings` does not **replace** project hooks; it is **additive**. With no isolation, the pass condition (the project hook stays silent) cannot be met.
  - **Adjudicator design rationale**: the plain-text CLI output (`out/mode-{a,b}.log`) is untrustworthy — the model merely restates the hook's block reason in its own words (observation: with the `"run: ls"` prompt the model did not call the Bash tool at all and instead fabricated an answer from the session's initial context). `run.sh` adjudicates by parsing the raw hook stdout/stderr of `--debug hooks --debug-file` directly, and that log is recreated on every run (deviation 4).
- **decided_by**: agent (Fable), 2026-09-20 — FAIL confirmed. **Recorded as something to reflect in §19 Q13** (this plan does not modify the master document — the actual §19 update is an item for Logan to confirm before Phase A begins).
- **Notes**:
  - **Fail decision rule applied (A2 §4.1 alternative path, verbatim from plan Task 5)**: in delegated runs, abandon the `PreToolUse`-based approval-escalation path and fall back to polling, where the bridge intercepts each `tool_use` event directly and escalates it to an approval. The rationale differs by mode:
    - In the `--bare` run (mode a) the hook surface **does not exist** — hook declarations in `--settings` are ignored, so polling is the only approval path. This is not a preference but a **forced choice**: `phase-a-interfaces.md` §8 sets the `claude_ds` runtime's `bare` default to `true`, so **a polling fallback is mandatory for `claude_ds`**.
    - In the non-bare run (mode b) the hook fires but is **not isolated** from the project hook (they are merged). If the project repo has its own `.claude/settings.json`, that hook runs as well, so nothing guarantees omnis is the sole approval path.
  - **A2-D11 conflict (copied verbatim; `_probes/2026-09-20-cli-probes.md` "Findings that change gate ⑪", item 2)**: "Under `--bare`, Anthropic auth is strictly `ANTHROPIC_API_KEY` or `apiKeyHelper` via `--settings`; OAuth and Keychain are never read." This run reconfirmed it — running `--bare` with a subscription-logged-in `claude` exited immediately with `Not logged in · Please run /login`, and switching to the wrapper that has the API key exported (`claude-ds`) let the identical command run to completion. A2-D11 assumes "delegated runs use the subscription binary as-is", but under `--bare` that assumption breaks — **revisiting A2-D11 is out of scope for this plan and is left as an item to escalate to Logan before Phase A begins**.
  - **Deviation 1 (path bug, minimal fix)**: the `hooks-settings.json` supplied by step 5 of the plan contains `"command": "node tools/spikes/gate-11-claude-bare-hooks/hook-receiver.mjs"` (a cwd-relative path), so on runs where Claude Code's cwd is the fixture worktree it dies with `Error: Cannot find module …` and **the omnis hook itself crashes**, producing a false negative (root cause confirmed with `claude --debug hooks`). The tracked file `hooks-settings.json` is left exactly as written in the plan, except that its `"$comment"` field states it is "illustrative only"; `run.sh` generates an absolute-path version at `out/hooks-settings.json` at run time and passes that one to `--settings`.
  - **Deviation 2 (prompt reliability)**: with the plan's original prompt `"run: ls"`, the model sometimes did not call the Bash tool at all and fabricated an answer, so it failed to test whether the hook fired. Switched to a directive prompt ("you must call the Bash tool"), and since commands containing `$`/backticks trip a separate built-in guard unrelated to this hook ("Contains simple_expansion"), used the pure literal `echo GATE11_PROBE_MARKER`.
  - **Deviation 3 (adjudication source)**: the original plan's `check()` grepped the plain-text CLI log. That is untrustworthy because the model may restate the hook's block reason and drop or alter the marker. Changed to grep the raw hook stdout/stderr from `--debug hooks --debug-file` (our hook exits 2 so it is classified `"(PreToolUse) error:"`, and the project hook exits 0 so it is classified `"(PreToolUse) success:"`, but the marker text is preserved verbatim either way).
  - **Deviation 4 (run isolation — adjudicator accuracy)**: `claude --debug-file` **appends** to the target file. Grepping an accumulating file counts markers left by earlier runs as this run's results, so even if Claude Code later fixes isolation and the gate is re-run, today's date would keep reporting FAIL because of stale lines. `run.sh` now deletes `out/` entirely at the start of every run, recreates it, and writes only inside it (debug log, CLI log, generated settings, and even the `latest` symlink Claude Code drops next to `--debug-file`). `out/` is already covered by `tools/spikes/**/out/` in `.gitignore`, so running `./run.sh` no longer dirties the worktree (verified clean `git status --porcelain` after a run).
  - **Deviation 5 (mode (a) driver)**: `--bare` does not read OAuth/Keychain, so a subscription login alone cannot measure mode (a). This MacBook does not have `ANTHROPIC_API_KEY` exported, but `claude-ds` on PATH is a wrapper that exports `ANTHROPIC_AUTH_TOKEN` from the Keychain and then `exec claude "$@"` — i.e. exactly the "Claude Code authenticated with an API key" that mode (a) requires. `run.sh` picks `claude` as the driver if `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` is present, otherwise `claude-ds`, and prints `mode_a_skipped=true` if neither is. (The model is `deepseek-flash`, but what the gate measures is the CLI's hook/permission surface, so it is independent of model choice.)
  - **Deviation 6 (mode (a) cwd)**: the plan runs mode (a) at the repo root with no project fixture, which would make `project_hook_fired=false` vacuously true. To actually measure both pass-condition terms, it was run in the **same fixture worktree** as mode (b).
  - The raw logs are kept as `evidence/mode-{a,b}-2026-09-20.txt` to avoid the `*.log` pattern in `.gitignore` (same practice as gate-07).
