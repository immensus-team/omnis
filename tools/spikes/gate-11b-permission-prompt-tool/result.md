# Gate ⑪b: the `--permission-prompt-tool` headless approval surface

- **Question**: Can a headless approval surface be attached to a delegated Claude Code run via `claude -p --permission-prompt-tool <mcp_tool>` — with the MCP tool served by a local stdio MCP server (`@modelcontextprotocol/sdk` 1.30.0, TypeScript) that logs every approval request to a file and answers allow/deny by rule (deny Bash, allow Read). Two modes — (a) non-bare + subscription auth, (b) `--bare` + claude-ds (API key) — are measured with the same probe design as gate ⑪ (fixture worktree with a project hook, a prompt that forces a Bash call, and a verdict drawn only from the MCP server's own log + `--debug` output).
- **Owning appendix**: A2 (§4.1 spike S-A2-1b), §19 Q13(③)
- **Owner**: agent (unattended)
- **Host**: macbook (Claude Code 2.1.274)
- **Run date**: 2026-09-20
- **Result (Pass/Fail)**: **PASS** — both modes satisfied the pass condition (the permission tool is invoked for the Bash call and its deny is honored). A stronger result than gate ⑪ (hook-based, FAIL) — `--permission-prompt-tool` stays alive even under `--bare`.
- **Measurements/Evidence** (`./run.sh`; the results below come from 3 independent runs — each run deletes and recreates `out/`, so every re-run is a genuine re-measurement — all three identical):
    ```
    mode_a_permission_tool_invoked_for_bash=true
    mode_a_bash_denied=true
    mode_a_project_hook_fired=true
    mode_a_debug_shows_mcp_tool_call=true
    mode_a_latency_ms=10005            (whole-turn wall-clock, 3-run range 8.0–10.3s)

    mode_b_permission_tool_invoked_for_bash=true
    mode_b_bash_denied=true
    mode_b_project_hook_fired=false
    mode_b_debug_shows_mcp_tool_call=true
    mode_b_latency_ms=2965             (whole-turn wall-clock, 3-run range 2.5–3.6s)
    ```
  - **mode (a)** (non-bare, driver=`claude`, subscription OAuth, cwd=fixture worktree with its own project hook): `--debug hooks,mcp,permissions --debug-file` leaves three decisive lines (`evidence/mode-a-debug-2026-09-20.txt`) —
    ```
    "Hook PreToolUse:Bash (PreToolUse) success:\nGATE11B_PROJECT_HOOK_FIRED tool=Bash"
    MCP server "omnis_gate11b": Calling MCP tool: approval_prompt
    MCP server "omnis_gate11b": Tool 'approval_prompt' completed successfully in 4ms
    ```
    Our MCP server's own request log (`evidence/mode-a-requests-2026-09-20.txt`, the file named by `GATE11B_LOG_PATH` — written by the server itself, not by model stdout) holds exactly one line: `{"tool_name":"Bash","input":{"command":"touch /tmp/gate11b_probe_marker.txt",...},"decision":"deny"}`. Bash was not executed, and model stdout (`evidence/mode-a-stdout-2026-09-20.txt`) independently reports "denied by a permission rule … omnis gate-11b" (not used for the verdict, reference only).
    **The project hook does not die** (the same absence of isolation as in gate ⑪'s non-bare result) — the fixture project hook in `.claude/settings.json` fires alongside our permission-prompt-tool. But that hook only exits 0 ("success"), which means "does not block" rather than holding approval authority (official permission evaluation flow: hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool`) — in fact it did not prevent our tool's deny from carrying the final decision. That is, **isolation still fails (the project hook keeps running), but even with that hook sitting open at exit 0, our rule holds final approval authority at the canUseTool step** — the path where the project hook blocks first on its own with exit 2 (the possibility of the project intercepting before our tool is reached) did not occur in this fixture, but remains a theoretical vulnerability (see Remarks).
  - **mode (b)** (`--bare`, driver=`claude-ds`, API key auth, same fixture worktree): the same three lines appear, but the hook line is absent entirely (`evidence/mode-b-debug-2026-09-20.txt` has 0 occurrences of the strings `PreToolUse`/`GATE11B_PROJECT_HOOK_FIRED` — an exact match with gate ⑪'s finding that "`--bare` ignores all hooks") — yet `--permission-prompt-tool` is alive:
    ```
    MCP server "omnis_gate11b": Calling MCP tool: approval_prompt
    MCP server "omnis_gate11b": Tool 'approval_prompt' completed successfully in 4ms
    ```
    One line in the request log (`evidence/mode-b-requests-2026-09-20.txt`), `decision:"deny"`. **This is the gate's key new fact**: `--bare` ignores hooks injected via `--settings` (gate ⑪), but it does not ignore an MCP tool registered via `--mcp-config` and designated by `--permission-prompt-tool` — the measurement matches the `claude --help` wording, whose `--bare` skip list (`hooks, LSP, plugin sync, attribution, auto-memory, background prefetches, keychain reads, CLAUDE.md auto-discovery`) contains no MCP/permission-prompt-tool.
  - **Latency of permission-prompt-tool itself**: in both modes the server takes **3–4ms** to receive a request and answer (the `--debug` log's `Tool 'approval_prompt' completed successfully in Nms`) — negligible. The 8–10s (a) / 2.5–3.6s (b) recorded as `latency_ms` is **whole-turn** wall-clock (including model inference + streaming); the permission round-trip is not the bottleneck. mode (a) being slower than mode (b) appears to stem from subscription routing/model differences and is not what this gate measures.
  - **Judge design**: same principle as gate ⑪ — the model's natural-language response is reference only and never used for the verdict. `run.sh`'s `check()` (1) greps the request log the MCP server writes to the file itself (`GATE11B_LOG_PATH`) for the `tool_name":"Bash"` line and its `decision` field, and (2) greps the raw output of `--debug hooks,mcp,permissions --debug-file` for `Calling MCP tool: approval_prompt` (Claude Code's own log that our tool really was called) and the project hook marker.
- **decided_by**: agent (Fable), 2026-09-20 — PASS confirmed. **This result satisfies the §19 Q13(③) item "the headless approval path is verified by Wave 1 spike S-A2-1b"** (the master document itself is not edited in this plan — updating the UNVERIFIED markers in §19/A2 §4.1 after Logan's confirmation is separate work).
  - **Proposed Q13 wording (reference only, docs/spec unmodified)**: "Headless approval path: when the bridge serves an MCP tool via `--permission-prompt-tool`, it is invoked for the Bash call and the deny is honored in both non-bare (subscription) and `--bare` (claude-ds, API key) modes (gate ⑪b PASS, 2026-09-20). In a `--bare` delegated run (the claude_ds default path A2-D11 requires) the hook surface is dead (gate ⑪) but the permission-prompt-tool surface is alive — so the bridge's approval-promotion path must be unified on **`--permission-prompt-tool` + `--mcp-config`** rather than a PreToolUse hook, so that it behaves identically under both drivers (subscription `claude`, `claude-ds`). Isolation from the project's own hook still fails under non-bare (the project hook runs alongside), but in the permission evaluation order a hook's exit 0 is 'did not block' rather than approval, so the bridge tool at the canUseTool step retains final decision authority."
- **Remarks**:
  - **Deviation 1 (probe command replaced, follow-up to gate ⑪ deviation 2)**: Using gate ⑪'s literal prompt (`echo GATE11B_PROBE_MARKER`) as planned reproduced `mode_a_permission_tool_invoked_for_bash=false` — the `--debug` log showed `tool_dispatch_start … permissionDecisionMs=2` (effectively instant approval, 0 MCP calls). The cause is a separate fact unrelated to what this gate measures: Claude Code classifies `echo`-style commands as "read-only Bash commands" and auto-approves them at the step before `canUseTool`/`--permission-prompt-tool` (the allow-rules step; official docs, "Allow rules" stage: "a read-only Bash command"). Measuring whether `--permission-prompt-tool` really gets called requires a command absent from that auto-approval list, so it was changed to the file-writing `touch /tmp/gate11b_probe_marker.txt` (still a literal with no `$`/backticks, so gate ⑪ deviation 2's guard is still respected). Recorded plainly: this finding is not a result of the permission-prompt-tool gate but a probe design bug.
  - **Deviation 2 (no SDK fallback needed)**: `@modelcontextprotocol/sdk` installed cleanly from npm (pnpm registry reachable) — the plain JSON-RPC fallback was unnecessary. However, SDK 1.30.0 requires the `zod` peer at `^3.25 || ^4`, so the originally attempted `zod@3.24.1` (the version the SDK pulled in transitively) produced `ERR_PACKAGE_PATH_NOT_EXPORTED` (zod's `./v3` subpath export missing) — fixed by pinning `zod@3.25.76` directly in `package.json`. `tools/spikes/gate-11b-permission-prompt-tool/` follows the same pattern as gates 06/13, carrying its own `package.json` + `pnpm-lock.yaml` (`pnpm install --ignore-workspace`, outside the root workspace glob).
  - **Deviation 3 (TypeScript runner)**: Rather than adding `tsx`, Node 26's built-in TypeScript type-stripping was used as-is (`node mcp-permission-server.ts`, no flag needed) — this file uses only plain type annotations, with no enum/namespace/decorator, so type-stripping alone suffices.
  - **Deviation 4 (run isolation)**: For the same reason as gate ⑪ deviation 4, `run.sh` wipes and recreates `out/` (gitignored, `tools/spikes/**/out/`) at the start of every execution — `--debug-file` appends, and our MCP server's request log appends too, so otherwise markers from a previous run would contaminate this run's verdict. After execution, `git status --porcelain` is clean apart from the newly created `tools/spikes/gate-11b-permission-prompt-tool/` (a new directory).
  - **Deviation 5 (latency measurement)**: macOS BSD `date` does not support `%N` (nanoseconds), so `date +%s%3N` overflowed straight into the integer — replaced with `python3 -c 'import time; print(int(time.time()*1000))'` (python3 confirmed present on this Mac).
  - **Residual risk from the un-isolated project hook (outside measurement scope, recorded only)**: In mode (a), there is a theoretical path where the project's own hook blocks first with exit 2, so the request never reaches our permission-prompt-tool at all (hooks come first in the evaluation order) — this fixture's hook exits 0 (allow), so that path could not be exercised. It means that delegating non-bare into a repo Logan does not own lets that repo's project hook intervene ahead of the bridge's approval path, so it should be read together with the §19 Q13① constraint "only within the allowlist of repos Logan owns".
  - The raw logs are stored as `evidence/{run-summary,mode-a-debug,mode-a-requests,mode-a-stdout,mode-b-debug,mode-b-requests,mode-b-stdout}-2026-09-20.txt` to sidestep `.gitignore`'s `*.log` (same practice as gate ⑪). The secrets scan (`authorization:|bearer |sk-ant|sk-proj|api[_-]?key`) returned 0 hits.
