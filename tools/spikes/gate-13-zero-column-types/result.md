# Gate ⑬: Zero's replication of vector/tsvector/uuid[]/generated columns

- **Question**: When a table mixing `vector`, `tsvector` (generated), and `uuid[]` columns is added to a publication, does Zero replicate it correctly and allow it to be queried from the client — and if not, how should `items.search_tsv` be excluded?
- **Owning appendix**: A3 (§7, §14 S-A3-2·S-A3-6)
- **Owner**: agent(unattended)
- **Host**: macbook (M5 Max, local Homebrew postgresql@17 + zero-cache-dev, scratch DB/replica dedicated to this spike — `wal_level=logical` was already changed permanently by gate-06 and is reused as-is; no additional Postgres settings were changed by this task)
- **Run date**: 2026-09-20
- **Result (Pass/Fail)**: **PASS**
- **Measurements/Evidence**:
  - `npx tsx measure.ts` → `thread: {"id":"...","participants":["<uuid>","<uuid>"]}`, `items: [{"id":"...","threadId":"...","body":"hello from gate 13"}]`, `gate13_pass=true`, exit 0. `uuid[]` replicates and queries correctly as a JS array (length 2).
  - Created a publication with the column list `probe_items (id, thread_id, body)` and verified directly with `psql` via `SELECT attnames FROM pg_publication_tables` → `{id,thread_id,body}` (confirmed that `embedding` is excluded).
  - `search_tsv` (generated tsvector) appears nowhere at all — not in the schema, the logs, or the publication — because Postgres logical replication never publishes generated columns in the first place (a Postgres rule of its own, independent of the publication column-list syntax). This means no column list or separate-table normalization is needed to exclude `search_tsv` — per this spike's result, the S-A3-2 fail rule ("split into a separate table") is unnecessary.
  - `embedding vector(768)`: zero-cache prints `WARNING: zero does not yet support the "vector" data type. The "probe_items"."embedding" column will not be synced to clients.` at startup, and since `embedding` is not declared at all in the client schema (`schema.ts`), it never appears in `z.query.probe_items` (no `embedding` key in the query result — see the measurements above) — the type itself is unsupported in zero-cache 1.9.0, so it can never reach the client.
- **decided_by**: agent
- **Notes**:
  - **Most important finding relative to the plan text (the publication column list does not block the initial snapshot copy)**: Even though `embedding` was excluded from the publication via `CREATE PUBLICATION ... FOR TABLE probe_items (id, thread_id, body)`, the zero-cache boot log printed `Starting binary copy stream of probe_items: SELECT "body","embedding"::text,"id","thread_id" FROM "public"."probe_items"` — zero-cache fetches the initial full snapshot by issuing a direct SELECT against the upstream table rather than going through the publication, and that SELECT is not subject to the publication's column restriction (being a generic SQL query, it sees every column of the table). What actually keeps `embedding` out of the client is not the publication column list but **zero-cache not supporting the `vector` type in the first place** (the WARNING above). In other words, if the plan is to exclude a type-supported column (e.g. `text`, `json`) via a column list, it will not be filtered out at initial sync time; the publication column list does appear to apply to subsequent logical replication (the WAL stream) (standard Postgres behavior), but this spike only tested INSERT and did not verify the UPDATE-then-streaming path — if Phase A produces a design that actually excludes a sensitive, type-supported column from the `items` table via a column list, this gap must be re-verified (outside A3 §7 scope; this task stayed within the planned scope of testing only the 3 kinds vector/tsvector/uuid[]).
  - Verified directly via `pg_publication_tables.attnames` that `probe_items` publishes exactly `{id,thread_id,body}` (a verification step not in the plan; the basis for the finding above).
  - Re-confirmed and reused gate-06's three API drift items: without `enableLegacyQueries: true`, `z.query` is `undefined`; without `definePermissions`, all queries silently return 0 rows; and the query key is the actual table name string given to `table()` (`probe_items`/`probe_threads`). Additionally found this time: if a Postgres column name is not camelCase (`thread_id`), the Zero schema must map it explicitly with `.from("thread_id")` for the client field (`threadId`) to be populated (the same pattern as gate-06's `createdAt.from("created_at")`, now confirmed to apply to FK columns as well).
  - `zero-deploy-permissions` prints `Permissions are deprecated and will be removed in an upcoming release` in the startup log (a warning from 1.9.0 itself, not a problem created by this spike) — `definePermissions` is still required for now (remove it and you get 0 rows, re-confirmed in gate-06), so it is used as-is in this spike.
  - `tools/spikes/gate-13-zero-column-types/` has its own `package.json` (`pnpm install --ignore-workspace`) and its own `pnpm-lock.yaml`, and sits outside the root workspace glob (satisfying the Global Constraints "outside the build graph"). The `zero-cache-dev` process was terminated after measurement (returning to port 4848 unused). The replica file is `/tmp/omnis-spike-zero13.db` (outside the repo).
