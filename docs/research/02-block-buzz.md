# github.com/block/buzz teardown

Fetched 2026-09-20 via `gh` CLI (repo API + raw file contents). All facts below sourced live from the repo; no training-data recall used.

## 1. TL;DR

Buzz is a **self-hosted team communication platform** built by Block (formerly Square) that stores every event (messages, reactions, git commits, workflow runs, review approvals, etc.) as a signed event on the Nostr protocol (NIP-01). Its core philosophy is that "humans and agents share the same identity model and the same audit log" — an agent owns its own keypair and becomes a channel member. Rust monorepo (relay + Postgres + Redis + S3/MinIO), a Tauri+React desktop app, an agent-first CLI (`buzz-cli`, JSON in/out), and an ACP (Agent Client Protocol) harness that connects goose/Codex/Claude Code. It is a separate project from goose, Block's own agent framework, and treats goose merely as "one of the supported agents." Apache 2.0, ★33.7k, a six-month-old and very active project. Its value to omnis lies less in direct porting than in its **architectural ideas** (single event log, treating agents as channel members, YAML workflows, the ACP harness pattern).

Buzz **addresses a different problem space than omnis**: Buzz "builds a new team chat platform from scratch" (a Slack replacement), whereas omnis is "a personal inbox that unifies existing channels." What overlaps is the philosophy of "treating an agent as a channel member/inbox actor," the "single event log + audit trail" design, and the ACP harness pattern (a way to attach multiple CLI agents through a single protocol).

## 4. Recommendation for omnis

**Do not fork or run Buzz itself.** omnis is "a single-user inbox that unifies multiple external channels" and Buzz is "a new team chat app centered on its own relay," so the problem is different. Adopting Buzz would mean removing existing channels such as Slack/Kakao/Gmail and migrating everything onto a Buzz relay, which directly conflicts with the premise of the omnis brief (unify while keeping existing channels). Effort: if Buzz were forced as the foundation, L (large) — learning the Rust monorepo, operating the self-hosted deployment, and ultimately the additional work of bridging external channels such as Slack/Kakao into Buzz somehow. Risk: low (Apache 2.0, no ToS issues) but the maintenance risk is high — it is a six-month-old, fast-growing project, so the API changes quickly (daily releases), and 3,622 open issues signal that there are still plenty of rough edges.

**Instead, "steal only the ideas" (effort: none, already read).** Three things directly help omnis's design:
1. An identity design that **models an agent as a first-class participant in a channel/thread** — exactly the same philosophy as omnis's goal that "an agent session is also an inbox thread." Buzz's "agent = a member with its own keypair" maps directly onto omnis as "agent session = a sender with its own conversation thread."
2. The **ACP harness pattern** (`buzz-acp`: subscribe to an event source → hand relevant events to an agent as a prompt → the agent writes its response back as events through the CLI) is exactly the same pattern omnis can use to connect Claude Code/Codex/DeepSeek/Hermes sessions to the inbox (polling/webhook → normalize → agent prompt → write-back).
3. The **YAML workflow trigger model** (message/reaction/schedule/webhook) is usable as a trigger taxonomy to consult when designing omnis's nightly digest, auto-label, and follow-up automation.

If omnis does adopt event sourcing, there is no need to pull in all of Nostr: it is better to borrow **only the concept** — "every inbox item = an append-only signed (optional) or plain event, dispatched by type" — and implement it far more lightly on its own Postgres schema. Buzz's Nostr/Schnorr signature scheme is overkill for a single-user app that has no need for multi-party trust.

## 5. What to borrow (concrete pointers)

- **Agent-as-member model**: the "Generating Keys" section of `crates/buzz-acp/README.md` — a separate keypair per agent, registered via `add-member`. For omnis, consult this when designing "a separate sender identity per agent session + how it surfaces in the inbox."
- **ACP harness diagram**: the `Buzz Relay ──WS──→ buzz-acp ──stdio──→ Your Agent` diagram at the top of `crates/buzz-acp/README.md` — maps directly onto the design of omnis's "channel event → normalize → agent runtime → write back" pipeline.
- **Kind-based dispatch**: `ARCHITECTURE.md` §2 "The Protocol" / the Kind Ranges table, and `crates/buzz-core/src/kind.rs` (127 kind constants) — the extension pattern of "new channel type = add one new integer constant" is a minimal design worth consulting when omnis unifies heterogeneous sources (Slack/Kakao/Gmail/agent-session, etc.) into a single `event_type` enum.
- **JSON in/out CLI convention**: `crates/buzz-cli/README.md` — stdout=JSON, stderr=JSON errors, exit codes 0/1/2/3/4/5 (ok/user-error/network/auth/other/write-conflict); a small, practical convention omnis can adopt as-is when building agent-facing CLIs (e.g., `claude-ds` delegation, a Hermes API call wrapper).
- **Workflow trigger kinds**: one line in the top-level README's "Works today" table — "YAML workflows: message / reaction / schedule / webhook triggers" — a minimal reference point for designing omnis's nightly digest (= schedule trigger) and auto-label (= message trigger).
- **Multi-tenant isolation pattern** (not needed for omnis right away, but relevant for future multi-user expansion): `ARCHITECTURE.md` "A Buzz community is the tenant-visible workspace selected by the request host" — the approach of enforcing host-based community resolution at every subsystem entry point.
- **What to avoid**: the entire Nostr/Schnorr signature infrastructure (`buzz-core`, `buzz-auth`), turning git into NIP-34 events, and the Blossom media store — over-engineered relative to omnis's scope, with low value for the porting cost.
