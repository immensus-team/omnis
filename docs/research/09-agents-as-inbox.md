# Agent sessions as inbox threads: Claude Code, Codex, DeepSeek, Hermes, and agent-to-agent protocols

Researched 2026-09-20. All facts below carry a source URL and fetch date; VERIFIED = confirmed against an official doc/repo/API this session, UNVERIFIED = could not confirm a primary source.

## 1. TL;DR

What omnis needs is not a new protocol but a thin normalization layer ("session bus") that reuses each agent's (Claude Code, Codex, Hermes, DeepSeek) existing headless/session features as-is. Claude Code resumes a session with `-p --output-format stream-json --resume <id>`, and Codex uses `app-server`'s JSON-RPC thread/turn/item events plus `codex exec resume`. Hermes already separates `X-Hermes-Session-Key` (a stable scope) from `X-Hermes-Session-Id` (a rotating transcript id) on its OpenAI-compatible `api_server` (:8642), and this pattern is the single most important finding — it applies directly to omnis's session-to-memory correlation. ACP and A2A exist for cross-vendor interoperability and are over-engineered for omnis's one user, two machines, and fixed agent set. Instead, building a "delegate to another agent" tool as a single MCP server is the practical agent-to-agent path.

## 2. Facts

- Claude Code headless mode: `claude -p` runs non-interactively; `--output-format` is `text` | `json` | `stream-json`; `stream-json` requires `--verbose` for full events and `--include-partial-messages` for token deltas. `--continue` resumes the most recent finished background session; `--resume <session_id>` resumes a specific one, findable across any project on the machine (not just the CWD) since v2.1.223. The session id is captured from the `system/init` event or from `--output-format json`'s `session_id` field. **VERIFIED** — https://code.claude.com/docs/en/headless (fetched 2026-09-20).
- Claude Code `--bare` mode skips hook/MCP/skill/plugin/CLAUDE.md auto-discovery for reproducible CI-style runs; without it, a `-p` run still loads a project's `.claude/settings.json` hooks and `.mcp.json` servers with no trust prompt. **VERIFIED** — same source.
- `system/init`'s optional `capabilities` array lets a caller feature-detect protocol behaviors (e.g. `interrupt_receipt_v1`) instead of parsing version strings — a useful forward-compat pattern. **VERIFIED** — same source.
- Claude Agent SDK ships as CLI + Python + TypeScript packages, exposing hooks (`PreToolUse`, `PostToolUse`, `SessionStart`, `SessionEnd`, `Stop`, `SubagentStart`, `SubagentStop`, etc.) and an `unstable_v2_resumeSession(sessionId, {model})` call; MCP servers are configured via `mcpServers`. **VERIFIED (secondary, cross-confirmed against the official headless doc's own links)** — https://platform.claude.com/docs/en/agent-sdk/typescript, https://platform.claude.com/docs/en/agent-sdk/hooks (search-fetched 2026-09-20).
- Codex CLI 0.155 exists and is current as of research date: GitHub releases show `rust-v0.155.0` (2026-09-17) and `rust-v0.155.1` (2026-09-18), with `0.156.0-alpha.*` already cutting on 2026-09-19 — the alpha cadence (dozens of builds/day) signals the app-server protocol is still churning. **VERIFIED directly via GitHub API** — `gh api repos/openai/codex/releases` (fetched 2026-09-20).
- Codex `app-server` is a long-lived bidirectional JSON-RPC 2.0 process (same backend for web/desktop/VS Code/CLI) organized around three primitives: **Thread** (a conversation), **Turn** (one user input → all resulting agent work), **Item** (an atomic output unit: message delta, shell command, file edit, tool call, reasoning note). Client calls `turn/start` with a `threadId`; the server streams `item/started`, `item/completed`, `item/agentMessage/delta`, etc. Approval requests come server-initiated as JSON-RPC requests; command decisions are `accept | acceptForSession | decline | cancel | acceptWithExecpolicyAmendment`; file-change decisions are `accept | acceptForSession | decline | cancel`. **VERIFIED (secondary, multiple aligned sources incl. the official OpenAI blog)** — https://openai.com/index/unlocking-the-codex-harness/, https://developers.openai.com/codex/app-server (fetched 2026-09-20).
- `codex exec` runs non-interactively (stderr = progress, stdout = final message only); `codex exec resume --last "<prompt>"` continues the most recent session in the CWD, `codex exec resume <SESSION_ID> "<prompt>"` targets a specific one, `--all` searches across all sessions. **VERIFIED** — https://developers.openai.com/codex/noninteractive (fetched 2026-09-20).
- Codex can also run as an MCP server itself (`codex mcp-server`, distinct from `codex mcp` client config), letting other agents/tools invoke a Codex thread as a callable tool over stdio; the stdio channel is implicitly trusted (any process that can write to stdin can issue arbitrary Codex commands), so it should not be exposed over an unauthenticated network transport. **UNVERIFIED against an official OpenAI doc this session (aggregated from a third-party technical blog only)** — https://codex.danielvaughan.com/2026/03/30/codex-cli-as-mcp-server/ (fetched 2026-09-20) — worth a direct doc check before relying on it.
- Hermes Agent `api_server` exposes an OpenAI-compatible HTTP endpoint at `127.0.0.1:8642` by default (`API_SERVER_PORT`), bearer-authed via `API_SERVER_KEY`, advertised on `/v1/models`; started with `hermes gateway`. **VERIFIED, primary source** — raw `website/docs/user-guide/features/api-server.md` fetched via `gh api repos/NousResearch/hermes-agent/contents/...` (fetched 2026-09-20).
- **The single most reusable finding**: Hermes separates `X-Hermes-Session-Id` (transcript-scoped, rotates on `/new`) from `X-Hermes-Session-Key` (a caller-supplied stable scope, e.g. `agent:main:webui:dm:user-42`, max 256 chars, echoed back on every response). The session key is threaded into `AIAgent(gateway_session_key=...)` and the Honcho memory provider uses it to derive a stable long-term-memory scope independent of which literal transcript/session id served the request. Discoverable via `GET /v1/capabilities` → `"session_key_header": "X-Hermes-Session-Key"`. **VERIFIED, primary source, official docs** — https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server (fetched 2026-09-20).
- Hermes `/v1/responses` implements OpenAI's Responses API with `previous_response_id` server-side chaining (full tool-call history reconstructed server-side) and a `conversation` string param that auto-chains to the latest response in that named conversation — functionally a named, resumable thread. All streaming surfaces (`chat.completion.chunk`, Responses SSE, `/api/sessions/{id}/chat/stream`, `/v1/runs/{id}/events`) share one keepalive/heartbeat convention (`: keepalive` comment every 10s of silence). **VERIFIED, primary source** — same doc.
- Hermes memory/skills stack: Honcho (`plastic-labs/honcho`) dialectic user modeling, FTS5 session search with LLM summarization for cross-session recall, and a skills system compatible with the open `agentskills.io` standard; subagents can be spawned for parallel workstreams, and Python scripts can call tools via RPC to collapse multi-step pipelines into a single low-context turn. **VERIFIED, primary source** — https://github.com/NousResearch/hermes-agent README (fetched via `gh api .../readme`, 2026-09-20).
- Hermes gateway platforms confirmed from the README's own comparison table: Telegram, Discord, Slack, WhatsApp, Signal, plus CLI — one gateway process, cross-platform conversation continuity, voice-memo transcription. **VERIFIED** — same README.
- Hermes ships a migration path *from* OpenClaw (`hermes claw migrate`, importing `SOUL.md`, memories, skills, command allowlist, messaging settings, API keys) — strong evidence the two projects are direct competitors/siblings in the same "always-on personal agent gateway" niche. **VERIFIED** — same README.
- OpenClaw (`docs.openclaw.ai`) supports native multi-agent routing on one Gateway process: each agent has its own persona, workspace, `agentDir` state directory, SQLite-backed session history, and model/tool config; inbound messages route to the correct agent via binding rules matching channel, account, contact, or group. Current release `v2026.8.1` (2026-08-30). **VERIFIED (secondary aggregation across docs.openclaw.ai and Wikipedia, cross-confirmed by Hermes's own migration tooling)** (fetched 2026-09-20).
- MCP (Model Context Protocol) current spec is **2025-11-25**, standardizing two transports: stdio (subprocess, JSON-RPC over stdin/stdout) and Streamable HTTP (single endpoint, POST+GET, optional SSE); the older two-endpoint HTTP+SSE transport from 2024-11-05 is deprecated, kept only for backward compatibility. **VERIFIED (well-established, cross-confirmed across multiple technical sources)** (fetched 2026-09-20).
- ACP (Agent Client Protocol), created by Zed, standardizes editor/IDE ↔ coding-agent communication the way LSP standardizes editor ↔ language-server communication, and deliberately reuses MCP's JSON representations where possible. As of the ACP registry (~March 2026), 25+ agents implement it, including **Codex CLI**, Gemini CLI (first external integration), GitHub Copilot CLI (added Jan 2026), Goose, OpenCode, Cline, and others; editor-side support (as of Aug 2026) spans Zed (native/origin), JetBrains IDEs (native), and community plugins for Neovim/Emacs. **VERIFIED (secondary aggregation, cross-confirmed by the official protocol site + Zed's own blog)** — https://agentclientprotocol.com, https://zed.dev/blog/acp-registry (fetched 2026-09-20).
- Google's A2A (Agent2Agent) protocol passed 150 supporting organizations by April 2026 (Linux Foundation project), with all three major clouds (incl. Azure AI Foundry, Copilot Studio) integrating it; production deployments are reported in supply chain, financial services, insurance, IT ops, but the Linux Foundation's own release gives no deployment counts or usage metrics, and independent commentary explicitly contrasts A2A's "supporter count" adoption against MCP's much larger measurable developer/server ecosystem. **VERIFIED for the org-count/cloud-integration claims (Linux Foundation press release), UNVERIFIED for real usage depth** — https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations... (fetched 2026-09-20).
- claude-squad (`smtg-ai/claude-squad`) manages multiple Claude Code/Codex/OpenCode/Amp sessions from one terminal app, giving each session an isolated tmux pane **and** its own git worktree so parallel agents never collide on the same files. **VERIFIED** — https://github.com/smtg-ai/claude-squad (fetched 2026-09-20).
- Beeper's `ai-bridge` (`beeper/ai-bridge`) is a mautrix bridgev2 connector that makes talking to an AI model indistinguishable from talking to a person inside Beeper: each model is a Matrix contact, each conversation a room, responses stream live carrying reasoning/tool-calls/citations/images, and everything is fully resumable across restarts. This is close to a working reference implementation of "AI session as inbox thread," built on Matrix rather than a bespoke bus. **VERIFIED** — https://github.com/beeper/ai-bridge (fetched 2026-09-20).
- "Pi" in this niche most likely refers to the Pi terminal-coding-agent (transferred to Earendil Works, May 2026): a coding-agent CLI with LSP + DAP integration, subagents, browser tools, and 60+ model-provider support. It is a harness/cost-routing reference, not a multi-agent inbox router. **UNVERIFIED (low-confidence identification — the name is heavily overloaded in 2026 OSS; no single canonical "Pi = inbox session router" project was found)**.

## 4. Recommendation for omnis

Do not build or adopt ACP or A2A now. Both solve cross-vendor, cross-user agent interoperability; omnis has one user and a closed, known set of agents (Claude Code, Codex, Hermes, claude-ds) on two machines it controls. That's a session-correlation and transport problem, not an interoperability-standard problem. Effort if pursued anyway: **L**, with real protocol-churn risk (Codex's own app-server is still alpha-cycling multiple times a day as of this week).

Instead, build a thin **omnis agent-bridge**: one small Node/TypeScript daemon per machine (Mac mini, MacBook) that:

1. Wraps each local agent's *native* headless surface — `claude -p --output-format stream-json --resume`, Codex's `app-server` JSON-RPC client, and Hermes's `api_server` HTTP/SSE client (claude-ds is free: it's Claude Code pointed at a different endpoint, same wrapper works unmodified).
2. Writes every turn/item/message event into the same Postgres schema that already backs the unified inbox, with `channel_type = 'agent:claude-code' | 'agent:codex' | 'agent:hermes' | 'agent:deepseek'` and one row per native session id — so an agent session literally *is* an inbox thread, no separate data model.
3. Borrows Hermes's session-key/session-id split directly: every omnis-initiated agent turn gets a stable `session_key` (e.g. `agent:codex:mini:project-x`) independent of whatever native session id is active that run, so memory and thread continuity survive a resumed-vs-fresh native session. This is the one idea in this research worth copying verbatim.
4. Exposes a small MCP server (`delegate_to_codex`, `delegate_to_hermes`, `read_session_transcript`, `send_note_to_agent`) that every one of these agents can already call, since they're all MCP clients — this *is* the practical agent-to-agent protocol: one agent's turn calls a tool that starts or resumes a turn on another agent, on either machine, over Tailscale.

Effort: **M** (1–2 weeks for an MVP covering Claude Code + Codex + Hermes bridging plus the delegation MCP server; Hermes's gateway is mostly reusable as-is for the messaging-channel side, cutting scope there to **S**).

Risk: Codex's app-server protocol is unstable (daily alpha builds) — pin a Codex version and budget maintenance time for drift. Claude Code's own docs flag forward-compat via a `capabilities` array specifically because the stream-json contract still moves; use the same pattern in the bridge's own protocol. Hermes's WhatsApp/Telegram/KakaoTalk-adjacent automation carries the usual unofficial-bridge ToS/account-ban risk, but that risk is already accepted in the wider omnis plan and isn't new here. `claude-ds`'s Anthropic-compatible DeepSeek endpoint is a personal/local setup, not something this research could verify against an official DeepSeek doc — sanity-check it directly before the bridge depends on it.

## 5. What to borrow

- **Hermes** `X-Hermes-Session-Key` / `X-Hermes-Session-Id` split and its `GET /v1/capabilities` self-description pattern — `website/docs/user-guide/features/api-server.md` in `NousResearch/hermes-agent`. Copy the header design and the capability-discovery endpoint shape into the omnis agent-bridge protocol.
- **Hermes** named `conversation` param that auto-chains `/v1/responses` calls — same doc — maps almost directly onto "omnis thread id → latest agent response id."
- **OpenClaw** binding-rule model (route inbound messages to an agent by channel/account/contact/group) — `docs.openclaw.ai/concepts/multi-agent` — borrow for auto-routing Logan's inbox items to the right agent/session instead of hand-picking one.
- **Beeper `ai-bridge`** UX model (one model = one contact, one conversation = one resumable room, live-streamed reasoning/tool-calls) — `github.com/beeper/ai-bridge` — the closest existing blueprint for what an "agent session inbox thread" should feel like to Logan, even though omnis shouldn't take a Matrix dependency for this.
- **claude-squad** per-session git-worktree isolation — `github.com/smtg-ai/claude-squad` — reuse this so two omnis-triggered Codex/Claude Code sessions on the same repo never collide on working-tree state.
- **Claude Code** stream-json `system/init.capabilities` feature-detection array — `code.claude.com/docs/en/headless` — reuse the exact pattern (a versioned capability-string array) for the omnis bridge's own event protocol, since it will also need to evolve without breaking every consumer.

## 6. Open questions

- Should the omnis agent-bridge sit *in front of* Hermes's `api_server` (extra hop, unified auth) or should omnis's inbox UI call Hermes directly over Tailscale and only bridge Claude Code/Codex?
- How should a Codex `app-server` turn — potentially dozens of `item` events — collapse into one inbox message vs. a live-updating thread? This is a UX call, not just plumbing.
- Is agent-to-agent delegation (the MCP `delegate_to_*` server) MVP-critical, or should the first omnis milestone be the plain multi-channel inbox with agents as one more `channel_type`, deferring delegation to v2?
- Is `codex mcp-server` mode actually production-ready for a trusted local network use case, or still expected to run only as a subprocess of a single trusted client? Only third-party sources confirmed this in the current pass — needs a direct check against `developers.openai.com/codex/app-server` or the `codex-rs` source before betting the delegation path on it.
- Is the `claude-ds` (DeepSeek via an Anthropic-compatible endpoint) integration officially supported, or a community/self-built shim that could break on a DeepSeek or Claude Code update?
- Does omnis ever need real multi-vendor/multi-tenant agent interop (e.g., if Underpin later exposes agents to other companies)? If so, ACP looks like the lighter, faster-moving bet (already has Codex CLI and Gemini CLI as members) vs. A2A's heavier, enterprise-to-enterprise design.
