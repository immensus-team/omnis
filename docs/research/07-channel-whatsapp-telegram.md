# 07 — WhatsApp / Telegram personal-account integration (channel adapters)

## 1. TL;DR

WhatsApp has no API, so it has to be attached either through whatsmeow (Go) or Baileys (TS) by reverse-engineering the WhatsApp Web multi-device protocol. The official Business Cloud API exists to issue a new business number, so it cannot be used at all with a personal number (Logan's real in-use number). Both libraries carry ToS-violation exposure and ban cases have been reported, but with a read-mostly, low-volume pattern the risk is on the low side (exact probability UNVERIFIED). whatsmeow is further ahead on maintenance and stability, and is easy to run on the Mac mini as a separate Go binary sidecar. On Telegram, logging in as an MTProto user account with an official api_id is a normal path permitted by the ToS, and the ban risk is far lower than WhatsApp's. On the TypeScript side, gramjs was archived in 2026-07, so we have to switch to mtcute. For both channels the right structure is a resident sidecar process on the Mac mini + a local session file (encrypted) + pushing events into the omnis core via webhook/queue.

## 2. Facts

**WhatsApp — libraries**
- whatsmeow (Go, `tulir/whatsmeow`, MPL-2.0) is a Go library for the WhatsApp Web multi-device API. As of 2026-09-19 it had 7,363 GitHub stars and a push on the same day (actively maintained). VERIFIED — [github.com/tulir/whatsmeow](https://github.com/tulir/whatsmeow), fetched 2026-09-20 (gh api).
- whatsmeow was originally a fork of go-whatsapp, but most of it was rewritten to support multidevice, and the README states that parts of the code were ported from WhatsappWeb4j and Baileys. VERIFIED — same source.
- whatsmeow's supported features: sending/receiving private and group messages (text + media), group management and change events, invite links, sending/receiving typing notifications, sending/receiving delivery and read receipts, reading/writing app-state (contacts, pin/mute, etc.), and retry receipt on decryption failure. Not supported: broadcast list messages (WhatsApp Web itself does not support them either) and calls. VERIFIED — [github.com/tulir/whatsmeow README](https://github.com/tulir/whatsmeow), fetched 2026-09-20.
- whatsmeow opens a QR login channel with `GetQRChannel()`, which must be called before `Connect()`; the QR is automatically reissued on expiry, and the whole pairing session is limited to about 160 seconds. A success/timeout/error code arrives as the final event and the channel closes. VERIFIED (multiple go.dev godoc mirrors agree) — [pkg.go.dev/go.mau.fi/whatsmeow](https://pkg.go.dev/go.mau.fi/whatsmeow), fetched 2026-09-20.
- whatsmeow is event-based (`AddEventHandler`) and ships an official SQL store implementation (`store/sqlstore`), so the device store and message history can live in SQLite/Postgres. Server-side history backfill arrives via `events.HistorySync`, but how far back it can actually recover depends on WhatsApp's server-side retention policy (range UNVERIFIED). VERIFIED (structure) / UNVERIFIED (exact retention period) — [pkg.go.dev](https://pkg.go.dev/go.mau.fi/whatsmeow), fetched 2026-09-20.
- Baileys (TS, `WhiskeySockets/Baileys`, MIT) is a WebSocket-based TS library for the WhatsApp Web API. As of 2026-09-19 it had 11,093 stars and its most recent push was 2026-09-15 (active). Release 7.0.0 introduced numerous breaking changes, and the new guide is being moved to baileys.wiki. VERIFIED — [github.com/WhiskeySockets/Baileys](https://github.com/WhiskeySockets/Baileys), fetched 2026-09-20 (gh api + gh repo view).
- The Baileys README carries an explicit disclaimer discouraging use for "stalkerware, bulk, automated messaging", and states that the maintainers accept no legal responsibility for misuse. VERIFIED — [Baileys README](https://github.com/WhiskeySockets/Baileys/blob/master/README.md), fetched 2026-09-20.
- An alternative is `pedroslopez/whatsapp-web.js` (which drives a real WhatsApp Web in a browser via Puppeteer, Apache-2.0). As of 2026-09-19 it had 22,593 stars and its most recent push was 2026-09-13. Being Puppeteer-based, it consumes significant resources and drags in a Chromium dependency. VERIFIED (repo metadata) — [github.com/pedroslopez/whatsapp-web.js](https://github.com/pedroslopez/whatsapp-web.js), fetched 2026-09-20.

**WhatsApp — device limits / ban risk**
- WhatsApp supports one primary phone plus up to four linked devices by default (WhatsApp Web/Desktop, etc.). Subscribing to Meta Verified raises the linked-device limit to 10. VERIFIED — [WhatsApp Help Center: About linked devices](https://faq.whatsapp.com/647349420360876), fetched 2026-09-20.
- The WhatsApp Business Cloud API (the official API) is handled separately under an "unlimited devices" category, but that is a structure that provisions a new business phone number — not one that attaches a number an individual was already using. VERIFIED (structural fact) — [Meta for Developers: About the WhatsApp Business Platform](https://developers.facebook.com/documentation/business-messaging/whatsapp/about-the-platform), fetched 2026-09-20; supporting summary [unipile.com WhatsApp API 2026 guide](https://www.unipile.com/whatsapp-api-a-complete-guide-to-integration/), fetched 2026-09-20.
- Getting expanded messaging limits and Official Business Account status requires business verification, and that is a track premised on a "new business number". VERIFIED — same source.
- whatsmeow GitHub Issue #810 (the "Your account may be at risk" warning) covers account-warning cases reported by users of both whatsmeow and Baileys. Baileys Issue #1869 ("High number of bans on WhatsApp!") and #2309 (a report of permanent suspension after a status upload) also exist. These issue-tracker reports are user self-reports and are not a statistically verified ban rate. UNVERIFIED (exact ban probability) / VERIFIED (the existence of the issues themselves) — [whatsmeow #810](https://github.com/tulir/whatsmeow/issues/810), [Baileys #1869](https://github.com/WhiskeySockets/Baileys/issues/1869), [Baileys #2309](https://github.com/WhiskeySockets/Baileys/issues/2309), fetched 2026-09-20.
- Both unofficial clients (GB WhatsApp and the like) and Baileys/whatsmeow-based automation carry ToS-violation exposure, and the common thread in community reports is that detection rests on protocol-level signals (low response rate, messaging strangers far outside one's contact graph, bot-like timing, traffic from datacenter/VPS IP ranges). This is a summary based on third-party blogs and manuals, not official documentation, so it is marked UNVERIFIED. — [achiya-automation.com WhatsApp Spam Detection 2026](https://achiya-automation.com/en/blog/whatsapp-spam-detection-2026/), fetched 2026-09-20.
- It is logically reasonable that read-only/low-volume personal use (checking incoming messages, replying occasionally) carries lower risk than automation built for bulk sending, but no quantitative evidence (concrete ban-rate figures) was found. UNVERIFIED.

**Telegram — libraries**
- The official Bot API runs as a bot account: it can only see messages in channels/groups the bot has joined as a member (and only with privacy mode turned off), and it cannot see messages sent by other bots. In other words, it is structurally unsuited to personal-inbox use, "reading all my DMs and groups as-is". VERIFIED — [core.telegram.org/bots/faq](https://core.telegram.org/bots/faq), fetched 2026-09-20.
- To read every conversation exactly like a personal account (DMs, and every group/channel I belong to), MTProto user-account (userbot) login is required. Representative libraries: for Python, Telethon (`LonamiWebs/Telethon`, MIT, 12,058 stars as of 2026-09-19, most recent push 2026-02-21 — stalled for 6+ months) and Pyrogram (`pyrogram/pyrogram`, LGPL-3.0, 4,616 stars, most recent push 2024-12-23 — stalled for about 2 years). For TS/Node there was `gram-js/gramjs` (MIT, 1,764 stars), but it **was archived on 2026-07-14 (official archived status confirmed)**. VERIFIED — all from gh repo view metadata, fetched 2026-09-20.
- After the gramjs archive, the actively maintained TS MTProto alternative is mtcute (`mtcute/mtcute`, MIT, 562 stars, push 2026-09-19 — active). A gramjs fork named teleproto is also mentioned in the community, but this investigation could not confirm it directly through official GitHub repo metadata (UNVERIFIED; only the documentation site docs.teleproto.dev was checked). VERIFIED (mtcute) / UNVERIFIED (existence of the teleproto repo) — [github.com/mtcute/mtcute](https://github.com/mtcute/mtcute), fetched 2026-09-20; teleproto mention [docs.teleproto.dev/faq](https://docs.teleproto.dev/faq), fetched 2026-09-20.
- TDLib (`tdlib/td`, Boost-1.0, 9,101 stars, most recent push 2026-08-24 — active, official Telegram) is a C++ core library, and using it from Node/TS requires a native binary or WASM binding plus a JSON bridge, making build/deploy complexity much higher than a pure TS stack. VERIFIED (repo metadata) / the complexity claim leans UNVERIFIED, based on community comparisons — [github.com/tdlib/td](https://github.com/tdlib/td), fetched 2026-09-20; comparison basis [mtcute.dev/guide/intro/mtproto-vs-bot-api](https://mtcute.dev/guide/intro/mtproto-vs-bot-api), fetched 2026-09-20.
- mtcute supports two login paths — QR (`qrCodeHandler`) and phone+code (`sendCode`/`phoneCodeHash`) — provides SQLite file-based session storage out of the box on Node.js, and offers 300+ high-level methods such as `markAsRead`. VERIFIED — [mtcute.dev/guide/intro/sign-in](https://mtcute.dev/guide/intro/sign-in), fetched 2026-09-20.

**Telegram — ToS / ban risk**
- Telegram's official API terms: an app must obtain its own `api_id`, and publicly distributing those credentials is explicitly prohibited. VERIFIED — [core.telegram.org/api/obtaining_api_id](https://core.telegram.org/api/obtaining_api_id), [core.telegram.org/api/terms](https://core.telegram.org/api/terms), fetched 2026-09-20.
- Every account that logs in using an unofficial API client is automatically put under observation to prevent ToS violations, and it is stated that using the API for flooding, spamming, or manipulating subscriber and view counters results in a permanent ban. Repeated login/logout within a short period can also flag an account as abuse. VERIFIED — [core.telegram.org/api/terms](https://core.telegram.org/api/terms), fetched 2026-09-20.
- If an account is banned by a false positive during normal use, there is an official path to appeal by explaining the situation to recover@telegram.org. VERIFIED — same source.
- Reading and replying to all messages one receives as a personal account (not automated bulk sending) differs in character from the "flooding/spamming/counter manipulation" Telegram explicitly prohibits, but the rule that one "is put under observation" itself applies to every unofficial-client login. VERIFIED (the wording) / the interpretation (that the risk is low) is our own — UNVERIFIED as a quantified claim.
- Bot API rate limits: no more than 1 message per second to the same chat (short bursts may be tolerated but are followed by 429), group chats 20 per minute, bulk broadcast about 30 per second (raised to as much as 1,000 per second when paid broadcast is enabled). On the MTProto user-account side there is no such official numeric documentation; it is controlled dynamically by server-side flood-wait (concrete figures UNVERIFIED). VERIFIED (Bot API figures) — [core.telegram.org/bots/faq](https://core.telegram.org/bots/faq), fetched 2026-09-20.

## 4. Recommendation for omnis

**WhatsApp: adopt whatsmeow (Go) as an independent sidecar process on the Mac mini.** Reasons: (1) the only practical path that uses a personal number as-is is web-protocol reverse engineering of the whatsmeow/Baileys sort, and the Business Cloud API is structurally ruled out (VERIFIED); (2) of the two libraries, whatsmeow has the better maintenance signals and lighter resource use; (3) even with a different language, attaching it over a sidecar plus local HTTP/gRPC or a Unix socket is no problem (the Mac mini already runs Hermes as a separate process anyway). Baileys stays as the fallback if "keep a single Node stack" becomes more important. whatsapp-web.js (Puppeteer) is out — a Chromium instance running at all times is wasteful on a 16GB RAM Mac mini, and community reports say it produces more detection signals (UNVERIFIED, but logically reasonable).
- Effort: **M** (whatsmeow itself is mature, but counting QR pairing UX + session persistence + the event→omnis queue bridge + reconnect/re-auth logic, this is several days of work)
- Risk: **ToS violation is certain (gray area); ban probability is UNVERIFIED but not zero.** Mitigations: keep response rates natural (no auto-replying instantly to every message), run on the Mac mini's home connection rather than a datacenter IP (already the plan), no bulk sending and no proactive messages to strangers, and keep the read-mostly + draft-then-human-send pattern (which naturally aligns with the brief's "draft only; sending decided after a notification" design). **Explicitly make Logan aware of this risk and get a clear answer on whether to proceed — account suspension is hard to reverse and affects business (Underpin/Onword) communications.**

**Telegram: adopt mtcute (TS) + MTProto user-account login.** Reasons: (1) there is an official api_id issuance path, so it is a normal track under the ToS (VERIFIED); (2) gramjs is archived and cannot be used for new projects (VERIFIED); (3) mtcute is the only actively maintained pure-TS option and ships built-in SQLite sessions, fitting the Mac mini sidecar structure directly; (4) TDLib is official, but the C++ bridge complexity is overkill relative to omnis's scope. Use the Bot API only for auxiliary purposes (e.g., our own notification bot); it is unsuitable for main inbox collection (it cannot read a whole group).
- Effort: **S–M** (MTProto itself is on the simpler side compared with whatsmeow, but it needs 2FA/phone-code UX, flood-wait handling, and api_id issuance/security)
- Risk: **Low ToS-violation exposure; ban risk clearly lower than WhatsApp's.** It is enough to avoid hardcoding or publicly distributing the api_id in code, and to avoid repeated login/logout in a short window (keep sessions long-lived).

Both channels line up exactly with the brief's design that **"the Mac mini is the only collection hub"** — channels without APIs (WhatsApp, KakaoTalk, LinkedIn) have sessions bound to a specific device anyway, so the right move is to run the whatsmeow/mtcute sidecars resident on the Mac mini and push events into the omnis core (Mac mini or cloud) via a queue/webhook. When we later move to a "MacBook-only app", the same sidecar binary/process can simply be launched on the MacBook as well (only the session file is newly issued per device), so the current design does not conflict with that goal.

## 5. What to borrow

- **whatsmeow's event model**: use the `AddEventHandler`-based event bus pattern directly as a reference for omnis's internal event bus (later a common `InboxEvent` type across all channels). Every channel repeats the same shape anyway — QR/phone-number login, reconnect, and message/receipt/typing events — so defining one **common adapter interface** (`connect() / onEvent() / sendMessage() / markRead() / setTyping()`) and having whatsmeow, mtcute, and (later) the Slack/Gmail adapters all implement it reduces the amount of code. Source: [pkg.go.dev/go.mau.fi/whatsmeow](https://pkg.go.dev/go.mau.fi/whatsmeow) events section.
- **whatsmeow's official SQL store pattern** (`store/sqlstore`): apply the same structure — session/device state in a local SQLite, restored on app restart without re-scanning the QR — to mtcute session management (mtcute already supports SQLite sessions built in, so it aligns naturally).
- **`Sealjay/mcp-whatsapp`** (a single-binary Go MCP server that wraps whatsmeow and exposes it as 42 MCP tools) — an architecture to reference directly for omnis's requirement that "the agent operates the inbox itself" (the brief's "the agent just handles everything in the inbox on its own" part). Exposing WhatsApp as MCP tools lets Codex/Hermes/Claude agents operate WhatsApp as standard MCP clients with no separate integration code — omnis itself is worth considering exposing its channel adapters as an MCP server. Reference: [github.com/Sealjay/mcp-whatsapp](https://github.com/Sealjay/mcp-whatsapp) (confirmed only via search results in this investigation; the detailed code was not reviewed — to be cloned and read in the next research round).
- **`steipete/wacli`** (a whatsmeow-based WhatsApp terminal client) — for reference on linking, pairing, and search UX. [github.com/steipete/wacli](https://github.com/steipete/wacli) (not reviewed, pointer only).
- **Baileys's explicit anti-misuse disclaimer wording and community norms** (recommendations against spam/bulk sending) — a tone to reference directly when writing omnis's own policy document (how far automation is permitted).
- **mtcute's dual login paths (QR + phone-code)**: given the brief's goal of "access from a MacBook/iPhone too", the initial pairing can happen on the Mac mini while the QR is rendered on the omnis app screen to be scanned with an iPhone camera (the same pattern as WhatsApp's actual multi-device UX) — borrow that as-is.
- **Kinso.ai's product flow of "priority ranking on read + reply drafts that learn your tone + morning briefing"** — overlaps exactly with the brief's archive digest and context-based reply draft requirements. Keep using it as a UI/feature benchmark.

2. Could not find an exact retention-period figure for whether whatsmeow's history sync actually backfills days' or weeks' worth of past messages — needs direct measurement in a prototype.

No official data exists anywhere for quantitative WhatsApp ban risk (e.g., real survival-time statistics for read-mostly, low-volume accounts) — a decision is needed on whether to take the risk with Logan's own number or pilot first with a separate secondary number (strong recommendation: **test with a secondary number first**).
4. On accounts with Telegram 2FA (cloud password) enabled, QR login requires extra UX; the design is undecided on how exactly to fold QR rendering inside the omnis app plus a 2FA entry flow into the iPhone/MacBook clients.
5. The communication protocol between the Mac mini sidecars (Go binary whatsmeow + Node process mtcute) and the omnis core (probably TS/Next.js) — local HTTP? gRPC? Unix domain socket? message queue? — must be designed in a way unified with the other channel adapters (referencing the Hermes api_server:8642 pattern), but that is outside this research's scope — a separate architecture research is needed.
6. Whether to keep the WhatsApp/Telegram session files (device keys, MTProto auth key) only on the Mac mini, or to pair them separately on the MacBook later (= consuming a separate linked-device slot) needs a decision — the "Mac mini-only collection, clients subscribe to results only" model looks safer, but it needs reconciling with the brief's "later a MacBook-only app" goal and with how sessions are migrated.
