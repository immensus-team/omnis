# KakaoTalk capture on a Mac mini (read + reply) — channel research

Fetched 2026-09-20 via WebSearch/WebFetch + `gh` CLI (GitHub repo API/README). All facts below are sourced live; no training-data recall used for anything dated or version-specific.

## 1. TL;DR

KakaoTalk has no official API for personal messages, and only "1 phone + 1 PC/tablet" can be logged in at the same time. The best route verified in practice is **kmsg** (`channprj/kmsg`, an open-source CLI + native MCP server that drives the KakaoTalk.app UI directly through the macOS Accessibility API, ★266, actively maintained) — it exposes read/watch(polling)/send/send-image as JSON and ships a built-in MCP server, so it can be attached to an omnis connector almost as-is. The risk is "account suspension," and the kmsg author himself states "known cases of permanent suspension" in the README. Implementing the LOCO protocol directly (node-kakao) is ruled out because real ban cases are documented. The Android emulator is structurally blocked because Kakao's "1 mobile" slot is already taken by the iPhone. The Notification Center DB and Vision OCR are only worth using as low-risk supplementary signals/fallbacks. The official Kakao Developers API (AlimTalk/FriendTalk/Login) is irrelevant to personal DMs.

## 2. Facts

- **One account per person; concurrent sessions limited to "1 smartphone + 1 PC/tablet"** — simultaneous login on two PCs is not allowed, and logging in on a new device requires email verification. VERIFIED. Source: Clien forum threads and multiple a-ha Q&A posts (aggregated search results), fetched 2026-09-20. The exact official wording should be re-confirmed against the original Kakao customer-service article (specific wording UNVERIFIED).
- **Two-factor authentication (2FA)** can be turned on under Settings > Kakao Account, and every new-device login requires additional verification (email, etc.). VERIFIED. Source: https://talksafety.kakao.com/toolandguide/account/auth (search snippet), fetched 2026-09-20.
- **Kakao Developers' official messaging API** (Kakao Talk Message API, AlimTalk/FriendTalk/Brand Message) operates under the principle that "a service cannot send messages directly to users," and can only send to "me" or to "friends (friends who have signed up for my service)" who consented via Kakao Login in the developer's own app — unrelated to receiving/sending arbitrary personal 1:1 DMs. VERIFIED. Source: https://developers.kakao.com/docs/latest/en/kakaotalk-message/common (WebSearch summary; a direct fetch of the original failed due to a redirect), fetched 2026-09-20. Full re-confirmation of the original text is marked UNVERIFIED.
- **`kmsg` (channprj/kmsg)**: a Swift CLI + native stdio MCP server that traverses/controls the real UI tree of KakaoTalk.app via the macOS Accessibility API (AXUIElement). Provides the `chats`/`read`/`watch`/`send`/`send-image`/`friend add`/`open-profile start` commands, JSON output, a `chat_id` local registry (`~/.kmsg/chat-registry.json`); `read --background-safe` reads only already-open windows without launching/activating KakaoTalk; `--capture-images` captures images via ScreenCaptureKit (requires Screen Recording permission); self-healing AX path cache. MIT license, ★266, 44 forks, most recent push 2026-08-23 (active). VERIFIED. Source: `gh api repos/channprj/kmsg`, repo README, fetched 2026-09-20.

VERIFIED. Source: `gh api repos/storycraft/node-kakao`, fetched 2026-09-20.

## 4. Recommendation for omnis

**MVP = install `kmsg` (the channprj fork) on the Mac mini via Homebrew and connect its built-in native MCP server (`kmsg mcp-server`) directly as omnis's KakaoTalk connector.** KakaoTalk.app is already installed on the Mac mini and that is what occupies Kakao's "1 PC slot" (with the iPhone in the "1 mobile slot"), so kmsg runs on top of it without consuming an additional account slot. Effort: **S** — just brew install, set KakaoTalk.app to stay logged in, and wire up the MCP connection. The `kmsg auth login` feature, which stores the Kakao password in kmsg's own encrypted store, is **not recommended** — KakaoTalk.app's own "stay logged in" is sufficient, and there is no reason to add an unnecessary password-storage surface.

Risk is **medium, requiring continuous monitoring**: the kmsg author himself states in the README that there are "many cases of permanent suspension from automation/unofficial protocol use," and AX being safer than LOCO is only the author's personal judgment, not an official Kakao guarantee. Mitigations: (1) do not set the polling interval excessively short (adjust `watch`'s default of 0.2s after observing real usage), (2) keep kmsg's default UX in which `send` always shows a dry-run result and executes only once after explicit confirmation, to prevent mis-sends/runaway behavior, (3) enable 2FA on the Kakao account to separately harden against session theft (this is account security rather than ban risk, but it is worth covering too).

**Fallback = macOS Notification Center DB + Vision OCR combination.** If the kmsg AX route breaks due to a KakaoTalk update (its self-healing cache exists but may not be complete), prepare a dual path that (a) uses the Notification DB as a low-cost "new message arrived" trigger and (b) extracts content via screen capture + Vision OCR (`macos-vision-ocr` etc., free/on-device). However, whether the general macOS behavior of not showing banners when KakaoTalk is in the foreground actually applies is unverified, so hands-on testing is required first.

**Explicitly excluded**: implementing the LOCO protocol directly (node-kakao etc.) has documented real permanent-suspension cases and the library itself has been left unattended for three years, so there is no reason to adopt it. The Android emulator route cannot run in parallel for structural reasons, since Kakao's "1 mobile slot" is already used by the iPhone (logging into KakaoTalk on the emulator logs out the iPhone session, or is blocked the other way around). The official Kakao Developers API (AlimTalk/FriendTalk/Kakao Login) is unrelated to personal 1:1 DMs, so it is not a consideration from the start.

**Long-term-memory backfill (separate track)**: apart from real-time capture, if you want to fill in past conversation history wholesale for omnis's goal of "inbox + local files + Drive + GitHub-based long-term memory," **indexing text exported via KakaoTalk's own "export conversation" feature** — as `k-skill`'s `katok` does — is far lower risk and lower maintenance cost than SQLCipher decryption (bypassing encryption is itself a gray area and breaks immediately if Kakao changes its encryption scheme). Direct SQLCipher decryption (the gist) is left only as an experimental track with effort L and UNVERIFIED success.

## 5. What to borrow (features, UX, architecture, code)

- **Reuse kmsg's native MCP server itself**: `kmsg mcp-server` (stdio; provides read/send-text/send-image tools) — omnis does not need to write AX automation from scratch; it can shell out to/embed this binary as the KakaoTalk connector. This is the key point that lowers effort from L to S.
- **The `chat_id` local registry pattern**: `~/.kmsg/chat-registry.json` — maps chat-room names (mutable) to stable synthetic IDs, keeps same-named chat rooms on separate IDs, and treats a renamed room as a new ID. A reference pattern that maps directly onto omnis's "unified thread ID across multiple sources" design.
- **`read --background-safe` mode design**: a mode that reads only already-open windows without launching/activating KakaoTalk — an exact match for omnis's requirement for polling that does not steal focus when the Mac mini is running several other automations (Hermes, postgres, Lima VM, etc.) concurrently. Make this mode the default polling mode for the omnis KakaoTalk connector, and switch to the foreground only for operations that require actual UI manipulation, such as `send`.
- **dry-run defaults for `send`/`friend add`**: always show the simulated result before actually sending, and execute only once after explicit confirmation — this aligns exactly, at the UX level, with omnis's "reply draft with notification" feature and with the principle this session itself follows, "message sending requires explicit approval." Adopt as-is.
- **AX self-healing path cache** (`AXPathCache`): caches frequently used UI paths and re-discovers them when a KakaoTalk UI change breaks a path — a general design lesson applicable to omnis's other UI-automation-based connectors (if any): make "auto re-discovery + logging when a structural selector breaks" the default pattern.
- **`katok` (k-skill)'s read-only/export-based archiving**: the structure that separates real-time capture (kmsg) from past-history indexing (katok-like) into entirely different pipelines — directly citable as the design rationale that omnis's "long-term memory" builder must operate separately from live channel connectors.
- **Apple Vision OCR CLIs** (`mac-ocr`, `macos-vision-ocr`): an on-device fallback/verification layer with no cloud cost — a component that matches omnis's brief direction of "cost-sensitive, local model/caching first," and can be plugged straight into the kmsg fallback.

## 6. Open questions

- Whether kmsg's AX reads/CGEvent sends actually work when the Mac mini's screen is locked (the login session alive but the screen locked) and no one is physically at the GUI session — not stated in the docs; hands-on testing required.
- How much real account-suspension history the kmsg (channprj) approach accumulates over the long term, beyond a year — currently only ★266 and a few months of community usage data; there is no quantitative data to support the author's claim that "AX is safer than LOCO."
- Whether `k-skill`'s `katok` truly never touches the SQLCipher DB and uses only KakaoTalk's own export feature, or builds its local archive some other way — the doc's wording is ambiguous, so it must be installed and its data source inspected directly.
- Whether macOS suppresses notification banners when KakaoTalk.app is in the foreground (i.e., whether the general macOS rule applies as-is to this app) — hands-on verification required; directly tied to the effectiveness of the Notification DB fallback.
- Whether Kakao's 2025-06-16 policy revision (tightened content censorship) changed the detection/sanction criteria for automation accounts — no official material could be found via search.
- Whether kmsg's `watch` polling (0.2–10s intervals when monitoring multiple chat rooms at once) causes stability problems from CPU/AX-tree contention when running concurrently with Hermes/postgres/Lima VM on a 16GB M4 mini — load testing required.
