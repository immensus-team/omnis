# GAP 7: Memory ingestion (local files / Drive / GitHub) + retrieval quality measurement (2026-09-20 research)

## 1. TL;DR

10-memory-oss.md settled only the storage layer (mem0 OSS + Postgres bi-temporal tables) and left ingestion open. The key finding of this research: **mem0 OSS removed graph memory entirely in v2.0.0 on 2026-04-14, and today it is available only in the Mem0 Platform (paid)** — 10-memory-oss.md's description of the graph as an "optional feature" no longer holds. In other words, relationship queries for the Network feature cannot be covered by mem0, and as previously recommended, a custom Postgres entity table is mandatory. For both Drive and GitHub, webhooks (push) require a public HTTPS endpoint with a valid SSL certificate, which does not fit the Tailscale-only Mac mini topology — polling must be the default. For embeddings, since mem0 TS natively supports Ollama, running nomic-embed-text-v1.5 (268M-parameter class, 768 dimensions, Matryoshka-shrinkable down to 64, MTEB 62.28) locally on the mini via Ollama is a far cheaper path than a custom MLX integration. However, latency on the actual mini (M4 16GB) could not be measured in this research — a hands-on benchmark is needed.

## 2. Facts

- **Removal of graph memory from mem0 OSS**: In mem0 SDK v2.0.0/v3.0.0 (per the 2026-04-14 changelog): "Graph memory is removed from the open-source SDK. It is not being replaced by an OSS equivalent: graph memory is a Mem0 Platform feature, built in and always on, with no external graph database required." The `enable_graph`/`graph_store` settings and the Neo4j/Memgraph/Kuzu/Apache AGE/Neptune drivers (~4,000 lines) were all deleted. All that remains in OSS is "entity matching" (for boosting hybrid search, not relationship traversal). **VERIFIED**, https://docs.mem0.ai/open-source/graph_memory/overview + https://docs.mem0.ai/changelog (fetched 2026-09-20). Confirmed in code as well: the `mem0-ts/src/oss/src/graphs` directory currently returns 404 (does not exist), `gh api repos/mem0ai/mem0/contents/mem0-ts/src/oss/src` (fetched 2026-09-20).
- **Embedding provider list in mem0 TS OSS**: `aws_bedrock, azure, fastembed, google, huggingface, langchain, lmstudio, ollama, openai, together, vertexai` — Ollama and LM Studio are first-class supported, so mem0 can call a local embedding server directly. **VERIFIED**, `gh api repos/mem0ai/mem0/contents/mem0-ts/src/oss/src/embeddings` (fetched 2026-09-20).
- **pgvector index dimension limit**: The vector type can store up to 16,000 dimensions, but **HNSW/IVFFlat approximate indexes support at most 2,000 dimensions** with standard vector (4,000 for half-precision, 64,000 for binary). Both 768 dimensions (nomic-embed) and 1536 dimensions (OpenAI small) fall safely within this limit. **VERIFIED**, https://github.com/pgvector/pgvector/blob/master/README.md (fetched 2026-09-20).
- **nomic-embed-text-v1.5**: ~0.1B parameters (≈137M), 768 embedding dimensions (native), Matryoshka-shrinkable to 512/256/128/64 (MTEB 61.96/61.04/59.34/degraded respectively), max sequence length 8192 tokens, full-dimension MTEB 62.28. 274MB download per the Ollama library, requires Ollama 0.1.26+. **VERIFIED**, https://huggingface.co/nomic-ai/nomic-embed-text-v1.5 + https://ollama.com/library/nomic-embed-text (fetched 2026-09-20).
- **The Apple MLX embedding ecosystem exists but is fragmented**: `Blaizzy/mlx-embeddings` (★444, active, supports BERT/ModernBERT/Qwen3/XLM-RoBERTa, 4bit/mxfp4/nvfp8 quantization) is the largest, but RAM requirements and M-series latency benchmarks are not stated in the README. mem0 has no MLX-specific embedding provider (going through Ollama is the practical local path). **VERIFIED** (ecosystem exists), **UNVERIFIED** (measured latency/RAM) — https://github.com/Blaizzy/mlx-embeddings (fetched 2026-09-20).
- **Voyage AI embedding pricing**: voyage-3 $0.06/M tokens (legacy, 200M free), voyage-3-lite $0.02/M (legacy, 200M free), voyage-code-3 (code-specialized, legacy) $0.18/M with no free tier, current voyage-code-4 $0.12/M (200M free). **VERIFIED**, https://docs.voyageai.com/docs/pricing (fetched 2026-09-20).
- **OpenAI embedding pricing**: text-embedding-3-small $0.02/M tokens, text-embedding-3-large $0.13/M tokens (both input-only, no output tokens). **VERIFIED**, https://developers.openai.com/api/docs/pricing (fetched 2026-09-20).
- **Incremental sync via the Google Drive changes API**: Obtain a baseline token with `changes.getStartPageToken()`, poll `changes.list()` against the page token (older changes first, reuse `newStartPageToken` for the next poll), and include removed items with `includeRemoved`. `changes.watch()` is real-time push but carries no change content, only a "something changed" signal (you still have to call `changes.list()` again). **VERIFIED**, https://developers.google.com/drive/api/guides/manage-changes (fetched 2026-09-20).
- **Drive push webhook requirements**: The callback URL **must be HTTPS with a valid SSL certificate** (self-signed, untrusted CA, or expired certificates are not allowed) on a publicly reachable server. Domain pre-verification is not specified in the docs. The maximum expiration for a subscription to the `changes` resource is 604,800 seconds (1 week); if unspecified, the default is 3,600 seconds (1 hour). **VERIFIED**, https://developers.google.com/workspace/drive/api/guides/push (fetched 2026-09-20). → **Directly conflicts with the topology of the Mac mini being Tailscale-only (no public IP/domain)** — using `watch()` requires a separate public relay, and without one only polling is possible.
- **Drive API quotas**: 1,000,000 quota units per minute per project, 325,000 units per minute per user (within a project), 4 billion units per 24 hours (the pre-billing threshold). `files.get` 5 units, list 100 units, download 200 units. At single-user scale there is effectively no chance of hitting the ceiling. **VERIFIED**, https://developers.google.com/drive/api/guides/limits (fetched 2026-09-20).
- **GitHub REST API rate limits**: 5,000 requests per hour for authenticated requests (15,000 for an Enterprise Cloud GitHub App). Secondary limits: no more than 100 concurrent requests, 900 points per minute (GET/HEAD=1 point, POST/PATCH/PUT/DELETE=5 points), 80 content-creation requests per minute / 500 per hour. **VERIFIED**, https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api (fetched 2026-09-20).
- **GitHub official recommendations**: Recommends subscribing to webhooks instead of polling ("stay within the API rate limit"), using GraphQL instead of multiple REST calls where possible, reducing traffic with conditional requests (ETag), monitoring rate-limit headers, and exponential backoff. Webhooks require signature verification (webhook secret). **VERIFIED**, https://docs.github.com/en/apps/creating-github-apps/setting-up-a-github-app/best-practices-for-creating-a-github-app (fetched 2026-09-20). → GitHub webhooks also **require a public HTTPS endpoint**, so they have the same Tailscale problem as Drive.
- **RAGAS**: A RAG evaluation framework whose goal is to replace "vibe checks" with structured, metric-based evaluation. The docs state that it supports registering custom datasets (question + expected answer/source) and managing experiments, but this fetch could not confirm the definitions of individual metrics such as context precision/recall/faithfulness (a separate metrics detail page exists). **VERIFIED** (framework exists/purpose), **UNVERIFIED** (detailed definitions of individual metrics) — https://docs.ragas.io/en/stable/ (fetched 2026-09-20).
- **KakaoTalk backfill scale reference** (05-channel-kakaotalk.md, re-quoted from earlier research): a blog report that in a real single-user case, a local SQLCipher DB had cached roughly 3.1 years of history, 8,058 contacts, and 458 chat rooms. Usable as a reference estimate for omnis's local file / historical inbox backfill volume (the ToS risk of channel collection itself is the domain of doc 05). **VERIFIED** (contents of that blog post); representativeness for production scale is **UNVERIFIED**.

## 4. Recommendation for omnis

**(1) Connectors: polling as the default across the board, webhooks later.** Both Drive `changes.watch()` and GitHub webhooks require a public HTTPS endpoint with valid SSL, and the mini is Tailscale-only, so it cannot meet this requirement. At this stage the right answer is to poll `changes.list()`/the GitHub API on a cron (e.g., every 5–15 minutes) — the implementation is simple, and neither the Drive quota (325,000 units per minute per user) nor the GitHub rate limit (5,000 per hour) will ever be hit at single-user usage. Forwarding webhooks to the mini through a public relay (Cloudflare Tunnel/Worker) is deferred until real-time responsiveness is genuinely needed (e.g., when GitHub PR review requests must surface in the inbox within seconds). Effort: polling S, webhook + relay L. Risk: low (official APIs, minimal OAuth scopes, no ToS issues) — GitHub/Drive are the only channel group without the account-suspension risk of the KakaoTalk/LinkedIn class covered in docs 05/06/07.

**(2) Embeddings: mem0 + Ollama + nomic-embed-text-v1.5, run locally on the mini.** mem0 TS already ships an `ollama.ts` embedding provider, so this achieves "fully local + $0" far more cheaply than a custom MLX integration (which needs a separate pipeline and costs more effort). 768 dimensions fit comfortably within the pgvector HNSW 2,000-dimension limit, and Matryoshka lets you shrink to 256/128 dimensions when needed to make the index lighter (the mini has 16GB, so index size can genuinely become a problem — pull this lever once the data grows). **However, measured throughput/latency on an M4 16GB could not be confirmed by this research — run a real-hardware benchmark first (e.g., time to batch-embed 1,000 sentences), and I recommend a dual-path design that falls back to voyage-3-lite ($0.02/M, 200M tokens free) if Ollama cannot keep up.** Effort: S (wiring mem0 + Ollama); the benchmark itself is S. Risk: low (local, ToS-irrelevant), except that mem0 is a project shipping breaking changes fast enough to rip out graph memory entirely within the last six months, so pinning the version + quarterly re-verification is required (medium maintenance risk).

**(3) Network relationship queries go to a custom Postgres table, not mem0 — this is settled.** With the removal of graph memory from mem0 OSS (2026-04-14), the answer to "does mem0 + pgvector cover the Network feature's relationship queries" is plainly **no**. mem0 OSS does only vector search + entity matching (a search-ranking aid); relationship traversal works only in the Mem0 Platform (paid SaaS). The "Postgres entity table borrowing Graphiti's 4-timestamp bi-temporal columns" already proposed in 10-memory-oss.md is confirmed as the only viable path — the doc must now be updated from "optional" to "mandatory". Effort: M (schema + relationship query design). Risk: low (self-implemented, so no vendor lock-in).

**(4) Chunking: different per source type, into one common schema.**
- **Code (GitHub)**: cutting at function/class boundaries is correct (embedding a whole file as one blob blurs the embedding, and fixed line-count cuts slice functions in half). Using tree-sitter to capture AST boundaries is the standard (the pattern code assistants like Continue.dev and Sourcegraph Cody all use) — omnis already has GitNexus MCP (an AST-based code graph tool) wired up, so rather than building from scratch, evaluate reusing GitNexus's parse output as the first option.
- **Inbox threads (Slack/Kakao/Gmail, etc.)**: a dual structure of per-message units + thread-summary chunks. Individual messages are short, so embed them as-is, but when a thread ends or exceeds a certain number of turns, generate an additional LLM summary chunk so that "what happened" is retrievable in compressed form (a compression strategy similar to Hermes's frozen-snapshot pattern).
- **Documents (local files/Drive)**: paragraph-level recursive splitting (500–800 tokens, 100-token overlap) is the standard starting point — no special logic needed.
Effort: S–M (code is S if GitNexus is reused; the rest is library-level).

**(5) Identity resolution is not automated for now.** This is the problem docs 05/17 both flag as "cross-file, no owner," but at single-user scale (on the order of a few thousand contacts, per the 8,058-contact Kakao reference) ML-based entity resolution is over-engineering. Match first on deterministic keys like email address/phone number/Kakao ID/LinkedIn URL, and for the unmatched ones it is enough to build a single manual "this person = that person" merge button in the Network UI for Logan to use. Revisit automatic matching later once the data accumulates (when hundreds to thousands of unresolved matches have actually piled up). Effort: S.

**(6) Retrieval eval: the minimal set that makes the G3 criteria actually testable.** Build a 30–50 question golden set, with each question carrying both an "expected source (source type + document/message ID)" and an "as-of timestamp" (since G3 requires "the same fact as of the same point in time"). Don't bring in the full RAGAS stack (LLM-judge-based context precision/recall/faithfulness) from the start; step 1 is to measure only "did the expected source appear in the top-k results" (recall@k) directly in a 20-line script — this is the cheapest verification, corresponding to rung 3 of the ladder (stdlib/direct implementation), and it immediately resolves G3's "no tests at all" problem. Add RAGAS later, when you want more refined evaluation criteria (e.g., when you want to score the faithfulness of the answer itself). Effort: S (recall@k script), M (when integrating RAGAS).

## 5. What to borrow

- **mem0 embedding provider wiring**: use `mem0-ts/src/oss/src/embeddings/ollama.ts` as the configuration example as-is — no need to stand up a separate embedding service in front; just put `embedder.provider: "ollama"` in the mem0 init config (the same pattern as the local companion example in 10-memory-oss.md).
- **GitHub sync policy**: adopt GitHub's official "webhooks first, otherwise conditional requests (ETag) + backoff" recommendation as-is — webhooks are impossible for omnis right now, so implement ETag-based polling first.
- **Graphiti's bi-temporal schema** (already a borrow decision in 10-memory-oss.md): only the upgrade to "mandatory" from this research needs updating. Apply the four columns `valid_from/valid_until/recorded_at/invalidated_at` to the Network entity table as-is.
- **GitNexus MCP's AST parsing**: the `mcp__gitnexus__*` tools (code graph/impact analysis) already connected in this session very likely already produce the function/class boundary information code chunking needs — before writing a new code-chunking pipeline, first check whether GitNexus output can be reused.
- **pgvector dimension design**: use nomic-embed's 768 dimensions as-is, but if the mini's storage capacity runs short, Matryoshka 256/128 reduction can be applied without a schema change (same vector column, slice only the first N dimensions) — all you need is a re-indexing script.

- Measured batch embedding throughput/latency of nomic-embed-text-v1.5 (Ollama) on an M4 16GB mini — needs a benchmark script to settle. This research confirmed specs only, not measurements.
- The definitions of RAGAS's individual metrics (context precision/recall/faithfulness) and how much of it is overkill for a 30–50 question golden set — needs follow-up research or reading the docs directly.
- Whether to build the public relay for Drive webhooks (Cloudflare Tunnel, etc.) now, and the threshold for how long polling holds up (polling interval vs. felt need for real-time) — requires Logan's judgment.
- GitHub App vs PAT: to handle multiple repos (company + personal), the GitHub App installation approach is cleaner scope-wise, but this research only confirmed rate limits for PATs and did not cover the App issuance flow itself.
- The concrete stack for the local file connector (raw FSEvents vs. a library like chokidar) is outside this research's scope — must be covered separately.
- How powerful mem0 OSS's "entity matching" actually is (the ranking improvement over pure vector search) was only checked in code/docs, not measured — needs checking before deciding how much the Network feature will depend on mem0 search.
