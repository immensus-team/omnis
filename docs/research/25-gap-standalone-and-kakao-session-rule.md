# 25 — GAP 6: Kakao device-session rule & standalone (hub-less) degradation plan

Fetched 2026-09-20. WebSearch was exhausted session-wide before this pass started (confirmed again on the first query). All primary-source facts below come from direct `curl`/WebFetch of Kakao's own domains (talksafety.kakao.com, cs.kakao.com, kakao.com/policy, kakaocorp.com) — these are server-rendered Next.js pages, fetchable without a browser. `cs.kakao.com`'s FAQ article bodies (category 1056, "PC/tablet/watch usage") load via client-side JS after page load and could not be retrieved by `curl`; that specific gap needs a real browser or the user opening the page.

## 1. TL;DR

Kakao officially calls PC/Mac/tablet/watch "sub-devices", and we confirmed from Kakao's own primary sources that connecting a sub-device requires either the 4-digit security verification code that pops up on the phone every time, or a Kakao Certificate (VERIFIED). But the exact numeric limit — "only 1 mobile + 1 PC allowed concurrently" — could not be found in a primary source during this pass either (UNVERIFIED, same as 05/90). Instead, we confirmed one more important new fact: Kakao's official anti-abuse policy (talksafety.kakao.com/measure) explicitly lists "using KakaoTalk in abnormal environments such as PC emulators" as a usage-restriction trigger — the Android emulator path is already a policy-level red flag, independent of the slot question. WhatsApp (1 phone + 4 linked devices, officially confirmed) and Telegram (multi-session support is normal) make device migration cheap, but KakaoTalk and LinkedIn still require "one always-on device" to hold the session. G6 must be redefined as 5 channels + agents + calendar, not all 7 channels.

## 4. Recommendation for omnis

**Redefine G6 as follows: "Slack/Gmail/Outlook/Telegram/WhatsApp/Calendar and the 4 agent sessions support fully hub-less operation (running on a MacBook + iPhone alone). KakaoTalk and LinkedIn, as long as they have no API, require 'one always-on device' to hold the session, and that is not a design flaw in omnis but an external constraint on the Kakao/LinkedIn side."** Do not hide this — write it into the product definition as-is. If Phase D is "embed the hub + ship it", then what ships is "core + 5 channels + agents", and you must state that KakaoTalk/LinkedIn capture still needs a separate always-on node, otherwise you will pay the redesign cost later. Effort: **S** (design doc edits), Risk: none (it is just an honest redefinition).

**Keep option A (fixed on the Mac mini) for the Kakao/LinkedIn capture host for now, but start reflecting option E's frame in code and docs so that "someday, MacBook only" stays reachable.** Concretely: (1) design the KakaoTalk/LinkedIn connectors as "capture sidecar" processes physically separated from the core logic (05/06/07 already recommend this structure — unify it with the same pattern as the WhatsApp/Telegram sidecars), (2) make the sidecar feed the core (Zero+Postgres) the same event format no matter which device it runs on, so that "is the sidecar host the mini or the MacBook?" has no effect on the core architecture. Effort: **M** (splitting out the sidecar is an already-planned pattern, so it is not large), Risk: low.

**State the performance degradation for when the MacBook is traveling or asleep explicitly in the product.** The Mac mini is always powered so there is no problem, but if you truly switch to "pure local, no Mac mini" later and the MacBook becomes the sole always-on node, then: if the MacBook sleeps (without clamshell mode) or loses power while traveling, KakaoTalk/LinkedIn capture stops completely for that period (since the KakaoTalk app itself terminates). Slack/Gmail/Telegram/WhatsApp/Calendar are API-based and are unaffected by this gap (they can backfill on reconnect). Effort: documentation only, S; for an actual workaround (keeping an always-on low-power node), simply continuing to use the Mac mini is itself the cheapest workaround, so no separate development is needed.

**State the re-pairing cost explicitly in the product UX.** Every time you change the host or reinstall the KakaoTalk app: (a) enter the 4-digit security verification code that pops up on the phone, or approve with a Kakao Certificate (manual, seconds to tens of seconds), (b) for WhatsApp, re-scan the QR (160-second window), (c) for Telegram, copy the session file (SQLite) to migrate without a QR (using mtcute's built-in session storage, see 07) — LinkedIn needs confirmation from file 06, but it is generally a similar manual step of reissuing session cookies/tokens. We found no evidence that the iPhone's "mobile slot" is affected by any of these re-authentication steps (no wording says adding/removing a sub-device touches the mobile session) — this part is UNVERIFIED, but it is an UNVERIFIED in the optimistic direction.

**SQLCipher key distribution is not a problem to solve right now.** While the mini is the only hub, the key only needs to live in one place, so keep 15's existing recommendation (store in Keychain, migrate to SQLCipher) as-is (Effort S). To keep the option "the MacBook might become a hub someday" open, it is enough to pick the Zero+TailscaleKit combination as 13 already recommends and build the core data layer on Postgres — then later it simplifies from "sync the SQLCipher key across two devices" to "which device is the Postgres server running on" (just apply Postgres's own at-rest encryption or a SQLCipher extension on that server side only). There is no need to build this key-sync logic in advance (no reason to pull an Effort-L task forward now, YAGNI).
