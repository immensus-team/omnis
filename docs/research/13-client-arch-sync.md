# 13 — macOS + iPhone Client Architecture & Tailscale Hub Real-Time Sync

## 1. TL;DR

For the macOS client, **Tauri 2** (stable, 2.11.x) lets us reuse the web stack; even though it is not purely native, an Apple-native feel can be achieved well enough with SwiftUI-level customization. On iOS, Tauri 2's mobile support is not yet as mature as desktop, which is a risk; instead, shipping the MVP as an **installed PWA (on iOS 26, defaults to web-app mode)** is the cheapest option in development cost. That said, a PWA can only do Web Push (no APNs), and background execution is limited. Because real APNs is unusable without the Apple Developer Program ($99/year), switching in v2 to a native iOS shell (Tauri iOS or Capacitor) is recommended. For sync, layering a local-first sync engine such as **Zero (Rocicorp)** on top of hub-authoritative Postgres — rather than a homegrown WebSocket — is more favorable for an offline/background iPhone. For hub access, the official **TailscaleKit** (embeds tsnet into iOS/macOS apps without a VPN profile) is a promising find — it can work around the iOS certificate bug in Tailscale Serve HTTPS (#19147, unresolved).

## 4. Recommendation for omnis

**MVP (S, noticeable in 1–2 weeks)**: Finish one macOS app first with Tauri 2 (menu-bar resident, real-time inbox view). For iPhone, reuse the same frontend as an **installed PWA** — not creating a separate codebase is the biggest win at this stage. For push, start with Web Push (limited, but better than "no notifications") plus ntfy served directly from the hub (the Mac mini), so important notifications are duplicated. For hub access, **do not put TailscaleKit inside the macOS Tauri app** (Tauri is WKWebView, and embedding native tsnet there has few verified precedents); instead, stand up HTTPS on the Mac mini with `tailscale serve` and have the MacBook connect via the system Tailscale client (already installed — stated in the brief) — Serve is a path already confirmed to work. In case the iPhone PWA cannot reach Tailscale Serve `*.ts.net` (bug #19147), we leave as a risk a **fallback to Funnel (public, but restricted via access-control) or resolving the MagicDNS name directly instead of tailscale serve** — this bug is the project's biggest unverified risk.

**v2 (M, 3–6 weeks)**: Switch to an iOS-only native shell — Tauri 2's iOS target (same codebase, only adding Rust plugins) or, for the least invasive option, evaluate Capacitor. At this point, join the Apple Developer Program at $99/year to attach real APNs, and use **TailscaleKit** so the iOS app dials the tailnet directly without a system VPN — a path that completely bypasses Serve's SSL bug (connecting directly to the hub, so the certificate problem never arises). For sync, migrate from homegrown WS polling to **Zero (Rocicorp)** (Postgres backend + official RN support + server-authoritative, which matches omnis's "the hub is the source of truth" model exactly). CRDT is not needed yet (with a single user on 2–3 devices, true simultaneous-edit conflicts are rare) — Yjs/Automerge can come later, once note/draft collaborative editing exists.

**Later migration cost (pure local, no Mac mini)**: It is cheapest if the Zero + TailscaleKit combination was chosen — even when the hub changes from "Postgres on the Mac mini" to "Postgres/SQLite embedded in the MacBook app," Zero's client-server protocol and TailscaleKit's tsnet node concept stay the same, and the iPhone still connects to the "hub" (this time the MacBook) over the same tailnet. If the PWA/Tauri split is carried forward, this migration requires touching both codebases — so **abandoning the PWA in v2 and consolidating into a single Tauri 2 codebase (macOS + iOS) is itself a precondition for this migration**.

**Risks**: (1) Tauri iOS is explicitly described by the team as "not a first-class citizen" — the schedule needs buffer until App Store review precedents are verified directly. (2) The Tailscale Serve iOS SSL bug is an unresolved open issue, so if it reproduces, the MVP's hub access itself is blocked — a reason to move TailscaleKit validation earlier. (3) KakaoTalk/LinkedIn have no API, so the approach would be screen/session capture on the Mac mini, which may violate their ToS (account suspension risk) — this is outside this research's scope, but needs separate confirmation regardless of the client architecture.

## 5. What to borrow

- **Zero's `zslack` example** (a Slack clone built with Expo + RN + Zero) — can be pattern-copied directly as a reference implementation for omnis's inbox list/thread views. The repository is linked from the community section of the Zero docs ([zero.rocicorp.dev/docs/community](https://zero.rocicorp.dev/docs/community)).
- **TailnetKit**'s Swift concurrency wrapper design (unofficial, but the code is easy to read, `willmortimer/TailnetKit`) — for API design reference if the official TailscaleKit's documentation is still thin.
- **tunnelless** (`indiagrams/tunnelless`) — a minimal reference implementation of "embedding a tsnet node into an iOS/macOS app without a VPN profile," which can be cloned and attached as-is during the PoC stage.
- **Tauri's `tauri-plugin-mobile-push`** — the pattern for attaching APNs/FCM without swizzling (explicit AppDelegate delegation) can be adopted as-is in v2 to avoid iOS 26 compatibility issues from the start.
- **PowerSync's mobile-first design docs** — in case PowerSync is chosen over Zero, the thought process behind "how the offline queue was validated on mobile" (YAML sync rules) can be applied to pushing omnis's work/personal filter rules down to the server side.

## 6. Open questions

- Whether the Tailscale Serve iOS SSL bug (#19147) also reproduces on this project's specific iOS version/Tailscale app version must be verified first on a real device — the top-priority spike before starting the MVP.
- Cases of a Tauri 2 iOS app actually passing App Store review (especially the WKWebView + custom framework combination) are not sufficiently verified by search — needs direct TestFlight submission to confirm.
- TailscaleKit's production usage cases (whether a separate company/app has actually shipped it) are lacking — the latest push is 2026-08-31, so it is active, but calling it "battle-tested" would be premature.
- The final choice between Zero and PowerSync depends on omnis's actual write patterns (who edits drafts and how often) — this needs measurement, not research.
- The ToS risk of the KakaoTalk/LinkedIn capture approach is outside this research's scope, but it directly affects client architecture decisions (how long the hub = Mac mini is kept) — a separate legal/ToS research track is needed.

### Corrected recommendation

The two numeric/count-based claims that move the needle are #2 and #5. Neither overturns the MVP/v2 staging in Section 4, but both change how urgently and how the two flagged risks should be treated:

- **Tailscale Serve iOS bug (#19147) is not "unresolved with silence from the community/maintainers"** — it has an active thread and a plausible non-Tailscale root cause (a third-party DNS-over-HTTPS app breaking `.ts.net` name resolution before TLS ever starts). Before treating "Funnel or MagicDNS fallback" as a required MVP risk mitigation (Section 4/6), the actual next step should be: check whether Logan's iPhone runs any DoH/private-DNS app or profile, and reproduce (or fail to reproduce) the SSL error on a clean network configuration first. If it doesn't reproduce, the "biggest unverified risk" in Section 6 is smaller than stated and the MVP path (system Tailscale client + `tailscale serve`) is lower-risk than the doc currently implies.
- **PowerSync's "most mobile-production-proven" status is PowerSync's own positioning, not an independently verified fact** — it appears in neither cited source. This doesn't invalidate PowerSync as a v2 candidate (its Postgres-WAL + YAML-sync-rules architecture is confirmed from PowerSync's own docs), but the comparison table in Section 3 should attribute "most production-proven" to PowerSync's marketing rather than presenting it as settled fact, and the Zero-vs-PowerSync decision in Section 6 should stay open (as the doc already says) rather than leaning on that unverified superlative.
