# Agent harness for omnis: Vercel AI SDK, Eve, and alternatives

Fetched 2026-09-20 unless noted.

## 1. TL;DR

Vercel AI SDK is now on major v7 (npm `ai@7.0.107`, 2026-09-18) and is the best fit as the LLM-call layer, with its `ToolLoopAgent`/`Agent` interface, tool approval, provider registry, and AI Gateway. "Vercel Eve" is a real open-source framework (released 2026-06-17, filesystem-first, durable, running on top of Vercel Functions), but its strong serverless/Vercel-first assumptions make it a poor match for a 24/7 Mac mini hub (KakaoTalk.app, always-on sockets, local Postgres). Build omnis's "kernel" (event bus + scheduler + approval gate) directly on the Postgres that already exists, and wrap only the LLM calls thinly with AI SDK 7 — that is the cheapest and fastest route. Temporal/Restate/Inngest/Trigger.dev can come later, if and when they're needed. Steal the connector-plugin structure and the approval-gate pattern from OpenClaw (390k★) and Hermes Agent (already running on the mini).

## 4. Recommendation for omnis

**Skip Eve and the Workflow SDK as the primary "kernel."** Both assume a Vercel-Functions-shaped deployment (request-scoped, ephemeral compute). omnis's hub is the opposite: an always-on Mac mini holding persistent Slack/Telegram sockets, a KakaoTalk.app instance automatable only locally, and a Postgres + Lima VM already running. Risk if forced: **M** — self-hosting the Workflow SDK backend is unverified (see open questions), and maintenance risk rises with every breaking change to a 3-month-old beta.

**Use Vercel AI SDK 7 (`ai` + provider packages + AI Gateway) as the model-call layer only.** Right-sized for "call an LLM, let it use tools, stream, get tool-approval hooks" — most of what reply-drafts and classification need. Effort **S**, risk **low** (MIT/Apache, no lock-in).

**Build the kernel (event bus + scheduler + approval gate) directly on the Postgres already on the mini**, not on a new durable-execution platform. An `events` table with `LISTEN/NOTIFY` or polling, a cron scheduler (`node-cron`, or `pg_cron` if available), and a `pending_approvals` table gated before any auto-send covers most of what Temporal/Restate/Inngest sell, at a fraction of the operational cost for one user. Effort **M** (days), risk **maintenance** (Logan owns retry/backoff) but zero ToS exposure and zero vendor lock-in. Revisit Trigger.dev (self-hostable, 16k★, active) for the narrow "webhook ingestion + nightly digest cron" slice if hand-rolling becomes a drag; skip Inngest AgentKit — 5-month-stale repo.

**Use the Claude Agent SDK (TS) for the agent-session-as-inbox-thread feature.** Claude Code/Codex CLI sessions are already omnis's delegation targets — `maxTurns`/`disallowedTools`/hooks map directly onto "spin up a bounded, permission-scoped session, treat it as a thread." Don't add LangGraph.js or Mastra just for this — they solve in-process multi-agent graphs, while omnis's actual problem is cross-process delegation to separate CLI tools on separate machines, which none of the graph frameworks model natively. Effort **S–M**. Risk: repo license returned `null` from GitHub's API — verify LICENSE before redistribution (not a blocker for personal use).

**Reject Mastra / LangGraph.js / OpenAI Agents SDK / Temporal / Restate as the backbone.** Each is a well-built, larger-scope answer to a problem omnis doesn't fully have. Adopting any now is over-engineering for a one-user system on one Mac mini, and each adds a server process competing for the mini's 16GB RAM alongside Postgres, Lima, and Hermes.

**The real risk isn't the harness — it's channel automation.** KakaoTalk.app and LinkedIn have no first-party API for this; automating them carries account-ban/ToS risk independent of framework choice. Mitigate with rate limits and human-in-the-loop on anything that posts or sends, regardless of the harness decision above.

## 5. What to borrow

- **From OpenClaw** (github.com/openclaw/openclaw): the "harness-as-swappable-plugin" pattern — model/agent backend (Claude, Codex, local model) is a plugin behind a stable interface, not hard-wired. omnis needs exactly this to route Claude Code / Codex CLI / DeepSeek / Hermes interchangeably. Also study the community's 5-pattern multi-agent architecture compendium (gist.github.com/mmarcus006/8b3bb89cb213b6d4359bf1bb928079b3) before designing omnis's own agent-to-agent routing — don't reinvent from zero.
- **From Hermes Agent** (already on the mini, hermes-agent.nousresearch.com/docs/developer-guide/architecture): the `*_write_approval` boolean-gate pattern (default false) for any auto-generated write — reuse verbatim for omnis's reply-draft-send and memory-write flows, since it's already proven in production on Logan's own hardware. Also its profile model (1 profile = 1 config + identity doc + memory store + gateway process + cron defs) is a clean template for "one omnis persona/tenant."
- **From AI SDK 7**: `ToolLoopAgent`'s tool-approval policy API (call- or agent-level) — map directly onto omnis's "context-aware reply drafts with notifications" (draft = tool call pending approval, not auto-sent). Also its provider registry + AI Gateway give the cost-routing layer (cheap OpenRouter/Chinese models) without writing a router by hand.
- **From Trigger.dev's docs** (github.com/triggerdotdev/skills — "Best practices for building AI agents and background jobs"): concrete patterns for durable chat agents that survive redeploys, useful as a design reference even if the platform itself isn't adopted wholesale.
- **From Claude Agent SDK docs** (code.claude.com/docs/en/agent-sdk/typescript): the `disallowedTools`/`maxTurns` permission-scoping pattern for spinning up a bounded delegate session per inbox thread.

- Is Eve fundamentally incompatible with an always-on, socket-holding process, or does it have an escape hatch (e.g., a long-running background function mode) not surfaced in the sources checked here?
