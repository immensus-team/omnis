# GAP 8 — Sizing the event firehose, then choosing the sync engine and L0 schema

Researched 2026-09-20. The measured figures in this document come from headless run captures of `claude -p`/`codex exec` executed directly in this session; the remaining numbers were fetched from official docs/repositories during this session. VERIFIED = confirmed via a primary source or direct measurement, UNVERIFIED = not confirmed.

## 1. TL;DR

As measured, a single Claude Code headless turn (`stream-json --include-partial-messages`) produced 39 events / 63KB, but 92% of that (58KB) was `system/init` (the MCP tool list) plus hook events — emitted once per **process launch**, not per turn — while the actual content (deltas + result) was about 4.8KB. Per the docs, the Codex `app-server` alone has six or more delta types, including `item/agentMessage/delta`, `item/reasoning/textDelta`, and `item/commandExecution/outputDelta`, so a turn mixed with tool calls would normally emit anywhere from dozens to a hundred-plus events. We did run a real Codex turn in this session, but it could not complete due to the account usage limit, so only the schema was confirmed by measurement (partial). Key conclusion: **the absolute volume is on the order of a few thousand per day, which Zero and PowerSync can both handle with room to spare** (PowerSync's official benchmark: 2,000–4,000 ops/sec for small rows), but committing token-level deltas straight to Postgres rows and replicating them lets transaction and replication overhead eat into the G5 (2-second) budget. Deltas must be split off onto a separate ephemeral channel (WS or Postgres NOTIFY, 8,000-byte limit), with only the debounced summary going into the sync store.

## 2. Facts

- **Claude Code measurement (this session, 2026-09-20)**: we actually ran `claude -p "What is 2+2?..." --output-format stream-json --verbose --include-partial-messages` and captured 39 events / 63,367 bytes. Type distribution: `system` 30 (58,056B, of which `init` alone is 28,340B — bloated by the list of many MCP servers connected in this environment; an omnis-dedicated agent would be smaller), `stream_event` 6 (2,242B, one each of `message_start`/`content_block_start`/`content_block_delta`/`content_block_stop`/`message_delta`/`message_stop`), `assistant` 1 (752B), `result` 1 (1,772B), `rate_limit_event` 1 (506B). The one-word answer "Four" had only 1 `content_block_delta` — a genuinely concurrent response grows its delta count in proportion to response length. **VERIFIED (direct measurement)**.
- **Codex app-server measurement (this session, 2026-09-20, partial)**: we actually ran `codex exec --json --sandbox read-only --skip-git-repo-check`, capturing 11 events / 1,992 bytes through `thread.started` → `turn.started` → 6 error items (150–350B each) → `turn.failed`, then it stopped on the account usage limit (message saying it resets 2026-09-23) — a normal content turn never completed. **VERIFIED (direct measurement, partial)**.
- **Codex app-server event taxonomy**: every item shares two lifecycle events, `item/started` (full item payload) and `item/completed` (final version). Delta streams number at least 6 kinds: `item/agentMessage/delta` (text chunks), `item/plan/delta`, `item/reasoning/summaryTextDelta`, `item/reasoning/summaryPartAdded`, `item/reasoning/textDelta`, `item/commandExecution/outputDelta` (stdout/stderr chunks). Item types themselves also number 11 or more: `userMessage`/`agentMessage`/`functionCallOutput`/`plan`/`reasoning`/`commandExecution`/`fileChange`/`mcpToolCall`/`dynamicToolCall`/`collabToolCall`/`webSearch`/`imageView`. The docs give no guidance on typical event counts or payload sizes. **VERIFIED** — https://learn.chatgpt.com/docs/app-server (fetched 2026-09-20).
- **PowerSync official performance benchmarks**: small-row replication throughput "2,000–4,000 operations per second", large rows "up to 5MB per second"; client sync "2,000–20,000 operations per second per client"; maximum row size 15MB; default maximum of 1,000 buckets per user (adjustable up to 10,000 on request); "50k+" concurrent clients supported per instance. **VERIFIED** — https://docs.powersync.com/resources/performance-and-limits.md (fetched 2026-09-20).
- **PowerSync self-hosting sizing**: staging = 1 compute container (512MB/1vCPU) + 1 MongoDB node (2GB/1vCPU, replica set mode); production = 1 replication container (1GB/1vCPU) + 2 or more API containers (1GB/1vCPU each) + a 3-node MongoDB replica set (2GB+ per node); under heavy load, scaling each container up to 2GB/2vCPU is recommended, and 1 API container is added per 100 connections. **Important**: **MongoDB is the default** for the internal bucket storage DB, and this document excerpt does not confirm whether Postgres-as-storage is supported — so the Mac mini may have to run MongoDB in addition to Postgres. **VERIFIED (sizing numbers)** / **UNVERIFIED (whether a Postgres storage alternative is possible)** — https://docs.powersync.com/maintenance-ops/self-hosting/deployment-architecture.md (fetched 2026-09-20).
- **Zero (rocicorp/mono)**: `advancement cost scales with number of changed rows, not number of queries` (official wording) — it is a row-level write-amplification model, so cost is determined not by "how many queries are subscribed" but by "how many rows changed." The multi-node deployment example is Replication Manager 1vCPU/2GB, View Syncer 2vCPU/4GB (starting-point recommendations, not hard upper bounds). The CVR (client view record) DB needs its own connection (`ZERO_CVR_DB`), but the docs give no curve for storage growth relative to client count. No quantitative throughput ceiling is published — only the qualitative statement that it "holds up surprisingly well on a single node." rocicorp/mono ★3,390, Apache-2.0, pushed 2026-09-19, 232 open issues. **VERIFIED** — https://zero.rocicorp.dev/docs/deployment (fetched 2026-09-20), `gh api repos/rocicorp/mono`.
- **PostgreSQL NOTIFY**: payload limit of 8,000 bytes (default configuration); an identical channel + identical payload duplicated within one transaction is coalesced into a single notification; the official docs recommend not putting large data directly in the payload but sending only the key of the table record. The notification queue is 8GB, and if a listening session holds a long transaction, commits can fail under high-frequency NOTIFY. **VERIFIED** — https://www.postgresql.org/docs/current/sql-notify.html (fetched 2026-09-20).
- **PostgreSQL logical replication slot safety valve**: setting `idle_replication_slot_timeout` (default 0 = disabled) invalidates slots that have been idle for the specified duration at the next checkpoint, preventing unbounded WAL accumulation — but because the default is off, if Zero/PowerSync's replication consumer (zero-cache or the powersync service) dies or stalls for a long time on the Mac mini, the default configuration lets WAL pile up without bound and fill the disk. **VERIFIED** — https://www.postgresql.org/docs/current/runtime-config-replication.html (fetched 2026-09-20).
- **omnis target (G5)**: stated in `01-definition-draft.md` as "state reflected across devices within 2 seconds" (the brief's own wording, not a research subject, cited from an internal document).
- **estimate — daily event volume**: inbox messages ~2,000/day (stated in the brief) plus agent turns conservatively at 20–200/day (Claude Code/Codex/Hermes/DeepSeek combined, not measured — requires observing Logan's own usage pattern); with events per turn ranging from 6 for a short answer to 50–150 for a turn mixed with tool calls (estimated from the Codex taxonomy), the daily total is roughly 1,000–30,000 events — negligible as a per-second average at 0.01–0.35 events/sec, but during the few to tens of seconds a turn runs, token streaming can burst to 10–50/sec momentarily (an estimate based on model streaming speed, not measured). **UNVERIFIED (estimate, needs measurement)**.

## 3. Options / Comparison

| Item | Zero (rocicorp/mono) | PowerSync |
|---|---|---|
| Source DB | Postgres (existing schema as-is) | Postgres source + **a separate storage DB required** (MongoDB by default) |
| Throughput disclosure | Quantitative ceiling not published ("scales per row") | Official benchmarks published (small rows 2,000–4,000 ops/sec) |
| Self-hosting minimum footprint | Replication Manager 1vCPU/2GB + View Syncer 2vCPU/4GB (recommended) | Staging 512MB+2GB (Mongo), production 1GB×3+ (6GB+ with the 3-node Mongo) |
| Fit for the Mac mini (M4, 16GB, already hosting Postgres+Lima+Hermes+sidecar) | Relatively light; ends with a single Postgres | Memory pressure once Mongo is added — risk of 5–8GB of the 16GB being taken by the sync stack |
| RN/mobile support | Officially supported (Expo, op-sqlite) | Known for mobile-first design (positioning, not independently verified — see doc 13) |
| Fit for omnis scale (1 user, 2–3 devices) | Both engines are over-engineered — limits like 50k clients/10k buckets never come into play. The deciding criteria are not throughput but **the Mac mini resource footprint and Postgres-only operation** |

## 4. Recommendation for omnis

**Split storage into three tiers** (this is the core answer of this gap):

1. **Ephemeral tier (outside the sync store)** — the `item/*/delta` family (token-level text, reasoning, stdout chunks) is not committed to Postgres. On the Mac mini, relay it directly to only the "devices currently viewing an open session" via a thin WS fan-out (or Postgres `NOTIFY`; within the 8,000B payload limit, 10–300B per chunk is plenty). If no device is viewing the session, the deltas are simply discarded — being unreplayable is acceptable (if replay is needed, pull from tier 3).
2. **Durable/replicated tier (the same inbox schema, the thing Zero/PowerSync replicates)** — create the single "agent session = inbox thread" row proposed in 09 at `item/started` (or `turn/started`), and **UPDATE content fields only on a debounce** (e.g. every 500ms–1s, or at `item/completed`). Do not write per delta — this is the real lever for holding the G5 (2-second) target: with PowerSync's benchmark (2,000–4,000 ops/sec) or Zero's "cost by row count" model, a burst of a few dozen per second is no problem for either, but if replication lag, CVR recomputation, and client materialization each add a few hundred ms, token-level commits leave room to blow past 2 seconds. The debounce itself removes this risk.
3. **Cold/audit tier (not replicated)** — keep the full log of all raw events (deltas included) only locally on the Mac mini (a separate Postgres table or JSONL) and do not replicate it to clients. Handle "view the full transcript" with an on-demand API queried directly against the hub.

**Engine choice**: recommend Zero as first choice (effort: M). The reason is operational simplicity, not throughput — it ends with a single Postgres and does not add a new DB (MongoDB) to the Mac mini. For self-hosting, PowerSync's storage DB is in practice MongoDB by default (whether a Postgres alternative is supported was not confirmed this session — see Open questions), which is a heavy burden on a 16GB machine already hosting Postgres+Lima+Hermes+channel sidecar. That said, the fact that Zero's throughput ceiling is unpublished (whereas PowerSync has public benchmarks) remains a risk — at 1 user and 2–3 devices, neither will hit its ceiling, almost certainly (both products target at minimum thousands of users/devices), so in practice it is close to a meaningless risk.

**Risks**: (1) `idle_replication_slot_timeout` defaults to 0 (disabled), so if the zero-cache process crashes on the Mac mini and never comes back, Postgres WAL can pile up without bound and fill the disk — set this value explicitly and add slot health checks to monitoring (effort: S, but if missed, the severity is a disk-full outage that takes down the whole hub). (2) As with the Codex account usage limit (which we actually hit this session), rate limits on the agent CLI side can obstruct measuring "how many events actually come out," so this document's volume estimates are for reference only and need re-verification with Logan's real usage logs. ToS/account-suspension risk is unrelated to the sync engine itself (both are open-source self-host licenses, Apache-2.0/similar).

## 5. What to borrow

- The Claude Code `system/init.capabilities` array pattern (already flagged in docs 13/09) — reuse it the same way in omnis's internal event bus protocol for version negotiation.
- The Codex app-server's two-stage `item/started` + `item/completed` lifecycle design — mapping omnis's durable tier row status field (`streaming` vs `complete`) directly onto these two events simplifies the client UI's "thinking..." shimmer logic.
- The principle from PostgreSQL's official NOTIFY docs, "don't put large data in the payload, send only the key" — apply it directly to the ephemeral tier design (for cases where delta text exceeds 8,000B, e.g. large diff output, use a key reference).
- PowerSync's "bucket count" concept (per-user bucket limits of 1,000/10,000) — useful as a sense of the ceiling when designing "how fine-grained should subscriptions be," even if Zero is chosen.

## 6. Open questions

- Whether PowerSync supports Postgres as its own storage backend (without MongoDB) — not confirmed by this session's fetch; must be re-checked before deciding.
- Zero's quantitative throughput ceiling (rows per second, CVR DB size growth curve) appears nowhere in the official docs — effectively irrelevant at omnis scale, but confirming it once by measurement (run zero-cache locally and load test) is cheap insurance.
- This document's "1,000–30,000 events/day" estimate is unverified — the next step is to measure Logan's actual daily agent turn count (Claude Code + Codex + Hermes + DeepSeek combined) over a week of logs.
- Whether the debounce interval (proposed: 500ms–1s) actually holds the G5 (2-second) target is only an assumption until measured end-to-end with a local prototype — the real propagation latency must be measured after choosing either Zero or PowerSync.
- Need to decide whether to leave Codex `item/reasoning/*` events out of the durable tier entirely (reasoning content fully ephemeral) — a privacy/debugging trade-off.
