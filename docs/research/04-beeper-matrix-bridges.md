# 04 — Beeper Desktop API/MCP vs Self-Hosted Matrix Bridges

Fetched 2026-09-20. Research scope: Beeper Desktop API/MCP, the mautrix bridge family, lightweight homeservers (Synapse/Tuwunel), and the choice of chat ingestion layer for omnis.

## 1. TL;DR

The Beeper Desktop API already provides "what we were about to build" as a local REST + MCP surface: 12+ networks — WhatsApp, Telegram, Signal, Discord, Slack, LinkedIn, Instagram, iMessage (macOS) — for free, with token auth plus an experimental WebSocket real-time channel. Turn on Remote Access and the `0.0.0.0` binding plus Tailscale plugs straight into a Mac mini (hub) → MacBook/iPhone (client) topology — exactly matching the architecture omnis already planned. The decisive gaps are **no KakaoTalk support** (both the official and community paths are effectively dead, with account-suspension reports) and paid plans gating premium features (scheduled sending, etc.). mautrix self-hosting (AGPL-3.0, active bridgev2) grants full ownership, but running bridges + a homeserver directly on a 16GB Mac mini carries a heavy maintenance cost, and the LinkedIn bridge is already archived. Conclusion: for the MVP, use the Beeper Desktop API/MCP as the primary channel, and handle KakaoTalk separately (a self-built automation, or a community bridge as a last resort).

## 2. Facts

**Beeper Desktop API/MCP**
- A fully local REST API plus a built-in MCP server. "runs entirely on your device." Supports: WhatsApp, Instagram, Telegram, Google Messages, Google Voice, Google Chat, Messenger, Signal, LinkedIn, X, Discord, Slack, iMessage (macOS only). — https://developers.beeper.com/desktop-api/ (2026-09-20 fetch) — VERIFIED
- KakaoTalk is not on the list; Beeper's official open-source page also files KakaoTalk under the "community-maintained" category (not officially supported). — https://developers.beeper.com/open-source/ (2026-09-20) — VERIFIED
- Auth: a Bearer token issued under Settings→Integrations, or OAuth 2.0 + PKCE (RFC 8414 discovery at `/.well-known/oauth-authorization-server`). The MCP endpoints (`/v0/mcp`, `/v0/sse`) use the same token. — https://developers.beeper.com/desktop-api/auth (2026-09-20) — VERIFIED
- By default it binds to localhost only (`http://localhost:23373`). Enabling "Remote Access" under Settings→Integrations→Advanced switches the binding to `0.0.0.0`, computes the base URL from `X-Forwarded-*` headers, and relaxes CORS for OAuth discovery. Beeper provides no tunnel of its own and recommends Cloudflare Quick Tunnel / **Tailscale** / a plain reverse proxy. — https://developers.beeper.com/desktop-api/advanced/remote-access (2026-09-20) — VERIFIED. omnis already exposes the Mac mini only over Tailscale (memory: see vigor relay), so this can be reused as-is.
- API resources: Accounts, Bridges, Chats, Messages, Assets, Client (focus/search), Info, App. For real time, an experimental WebSocket endpoint exists alongside REST ("WebSocket (Experimental)") — a separate feature from the CLI's HMAC-signed outbound webhook + WebSocket watch. — https://developers.beeper.com/desktop-api-reference/ (2026-09-20) — VERIFIED (the detailed WebSocket spec is on a separate page, unchecked → UNVERIFIED: payload format)

## 3. Options / Comparison

| Axis | Beeper Desktop API/MCP | bbctl self-hosting (on Beeper infrastructure) | Fully self-owned mautrix + Tuwunel homeserver | Direct adapters (calling each network's unofficial API directly) |
|---|---|---|---|---|
| Build effort | S (install the app + a token) | M (Python venv, bbctl config, per-account login) | L (homeserver + N bridges each configured/operated) | L–XL (reverse engineering per network, highest account-suspension risk) |
| Real-time | REST + experimental WebSocket; MCP mixes polling and events | Matrix standard sync (the bridge pushes to Beeper's homeserver) | Matrix client-server sync (fast when native sliding sync is supported) | Depends on the implementation |
| Coverage | 12+ excluding Kakao | 16+ official + bridgev2 third-party (Kakao is community-only, effectively dead) | The entire mautrix ecosystem (license and maintenance vary per bridge) | Everything in theory; in practice a standing ToS-violation risk on each private API |
| License impact | Use of a service (no code ownership); just comply with the ToS | Same — tied to a Beeper account/infrastructure | Many AGPL-3.0 bridges — redistributing omnis to third parties as a SaaS triggers the source-disclosure obligation (irrelevant for personal use) | No license issues; ToS/security risk is shifted onto you instead |
| Fit for a 16GB Mac mini | One app, lightweight | Scales with the bridge count (community reports that 5–6 run comfortably on a standard VPS) — 16GB should have room to run everything except Kakao | Homeserver (Tuwunel 1–2GB) + N bridges + Postgres — the management burden shifts from code to "24/7 health checks on N processes" | Not applicable (varies per network) |
| Maintenance burden | Absorbed by Beeper (bridge updates, account-reconnect UX, etc.) | Half by Beeper; logins/re-auth are on you | All on you (bridge crashes, schema migrations, homeserver upgrades) | All on you plus continuous reverse engineering |

## 4. Recommendation for omnis

**The primary channel layer is the Beeper Desktop API + MCP running on the Mac mini.** Reasons: (a) it lines up exactly with the architecture omnis already planned — "Mac mini = ingestion hub, exposed only over Tailscale" — and the Remote Access option fits it precisely, so almost no separate tunnel/proxy design is needed. (b) It covers WhatsApp, Telegram, Slack, LinkedIn, Discord, Signal, Instagram, and iMessage in a day. (c) MCP is built in, so omnis's agentic layer (Vercel AI SDK) can attach to it directly via tool calls — omnis never has to write "code that manages bridges." Impact: **S effort**; the risk is ToS (personal use is explicitly recommended — bulk sending/auto-replies carry account-suspension risk, especially on WhatsApp/LinkedIn) — **Medium risk, a ToS-compliance item**. The experimental WebSocket may still be unstable, so design for polling + WebSocket in parallel initially.

**KakaoTalk is solved separately, outside the Beeper/mautrix ecosystem.** The community bridge (node-kakao-based) is unmaintained and has suspension reports, so it is not a fit for putting Logan's real account at risk. Alternative: build a **self-built adapter** that reads `KakaoTalk.app` (already installed on the Mac mini) via macOS Accessibility/AppleScript or by polling the local DB (SQLite) and normalizes it into the omnis inbox. Impact: **M effort, low account-suspension risk (using the official client as-is, read-first with no automated sending)**; the downside is fragility against macOS updates / KakaoTalk app updates (the breakage risk peculiar to UI automation exists separately).

**Full mautrix self-hosting (homeserver + all bridges yourself) is not adopted for now.** Beeper already offers the same bridge code as a managed service; running it yourself costs more in maintenance (bridge crash handling, Postgres, homeserver upgrades) than the benefit is worth. It is worth revisiting at the **"future product without the Mac mini"** stage, though: at that point the Beeper Desktop app itself becomes the "another company's app" dependency, and `bbctl` (use a Beeper account, but run the bridges on your own hardware) is the middle ground — keeping Beeper's infrastructure (login/reconnect UX, homeserver) while bringing the processes local. That is **M effort** and low risk, since it is a path the ToS explicitly permits (the official docs include self-hosting guidance). A fully self-owned homeserver (Tuwunel) plus self-hosting every bridge comes only at the stage after that, and only when a requirement arises to "remove the dependency on Beeper the company entirely" — **L effort, legal risk only on AGPL redistribution, low before then**.

**Direct adapters (reverse-engineering private APIs) are not adopted.** That is the exact opposite of this research's premise — "don't build new bridges" — and there is no reason to redo from scratch the protocol reverse engineering that mautrix/Beeper have been refining for years.

## 5. What to borrow

- **Auth/token model**: borrow directly from the Beeper Desktop API's "issue scoped tokens under Settings→Integrations→Approved connections" UX for omnis's "permissions for an agent to access the inbox" model. There is no need to implement OAuth discovery (`/.well-known/oauth-authorization-server`, RFC 8414) from scratch; adopt it when a client (another tool attaching over MCP) actually appears.
- **Remote Access pattern**: the `X-Forwarded-Host/Proto/Port`-based base URL computation is a pattern omnis can reuse as-is when bundling several local services on the Mac mini (Beeper API, Hermes api_server:8642, etc.) behind Tailscale into a unified gateway — see: https://developers.beeper.com/desktop-api/advanced/remote-access
- **Open-source MCP server implementations**: `@beeper/desktop-mcp` (npm); the source lives in the Beeper org on GitHub (`beeper/cli` is the CLI-side code to consult, useful for seeing the per-command REST mapping pattern) — when building omnis's own MCP layer (e.g. exposing the KakaoTalk adapter as an MCP tool), copy the tool-name/schema naming conventions verbatim.
- **The bridgev2 3-layer structure** (Bridge Framework / Network Connector / Network API Client) is a separation worth consulting when omnis designs "how to split each network adapter" — when writing the KakaoTalk adapter too, splitting "protocol layer vs Matrix/Inbox layer" along these lines makes adding other networks easier later.
- **The CLI's HMAC-signed outbound webhook** pattern (`beeper/cli`, `beeper/desktop-api-cli`) — a signature-verification approach omnis can lift as-is when implementing the "wake the agent when a new message arrives" hook.

## 6. Open questions

- Whether the Desktop API itself is fully open on the free tier, or whether certain features (e.g. multiple accounts, the search API) are gated behind Beeper Plus — not stated in the official docs; needs to be confirmed by issuing a token with an actual free account.
- The real payload/stability of the experimental WebSocket endpoint — it carries an "experimental" label, so a separate spike test is needed before depending on it in production.
- Where and how KakaoTalk.app stores local data (SQLite? encrypted?) — needs direct verification on the Mac mini as to whether the Accessibility path or reading the DB directly is actually feasible.
- After `beeper/imessage`/`beeper/mac-registration-provider` were archived, documentation is thin on exactly which repos (`beeper/platform-imessage` + `beeper/registration-relay`) the iMessage self-hosting path moved to — if we use the Beeper Desktop API's built-in iMessage support, this question likely becomes moot (low priority).
- Beeper company risk itself (service shutdown, pricing changes) — when and how much to reduce dependence on Beeper at the "future product without the Mac mini" stage needs to be revisited as product maturity allows.

### Corrected recommendation
