# 08 — Channel integration: Slack, Gmail, Outlook/M365, Google Calendar

Researched 2026-09-20. Scope: capture design for a single power user (Logan), Mac mini hub + MacBook/iPhone clients over Tailscale, no public server today.

## 1. TL;DR

Slack requires **Socket Mode** (WebSocket; it's an outbound connection, so no ports need to be opened on the Mac mini) instead of RTM, combined with an **xoxp user token**, to get both "every mention/DM that reaches me" and "send as myself" (a bot token alone won't do it). For Gmail, **watch() + Cloud Pub/Sub** is the best option — Pub/Sub is Google infrastructure, so no public endpoint is needed (pull subscriptions work). However, OAuth "Testing" mode kills the refresh token after **7 days**, so switching to Production is mandatory; sensitive scopes like gmail.modify are fine without verification as long as there are fewer than 100 users. Outlook/M365 requires a **public HTTPS endpoint** to use Graph webhooks, but unlike Google Calendar this does not require Search Console domain-ownership verification, so it can be exposed via **Tailscale Funnel** (maximum subscription lifetime 4230 minutes ≈ 3 days, renewal required). Google Calendar push requires domain-ownership verification, which effectively blocks Funnel, so **syncToken polling** is the realistic option. The openclaw repo (390k stars) has a Slack/IMAP/Google channel plugin architecture that can be used directly as a reference source.

## 2. Facts

**Slack**
- The RTM API is unusable for new apps; legacy classic apps are fully sunset on 2026-11-16, with Socket Mode (`apps.connections.open` → WebSocket) or the Events API (HTTP) as the replacement. VERIFIED. Source: [Slack changelog — legacy custom bots/classic apps deprecation](https://api.slack.com/changelog/2024-09-legacy-custom-bots-classic-apps-deprecation), [Legacy RTM API docs](https://docs.slack.dev/legacy/legacy-rtm-api/). Fetched 2026-09-20.
- Socket Mode allows up to 10 concurrent WebSocket connections per app (for load balancing / graceful restarts); the URL is newly issued on every `apps.connections.open` call and must be refreshed periodically. VERIFIED. Source: [apps.connections.open](https://api.slack.com/methods/apps.connections.open), [Socket Mode implementation](https://api.dev.slack.com/apis/connections/socket-implement). Fetched 2026-09-20.
- A bot token (`xoxb`) only sees channels it has been invited to and DMs sent to it; workspace-wide search, other people's DMs, and sending that "looks like it came from me" (as if the person typed it themselves) all require a user token (`xoxp`, e.g. the resource-based scopes `search:read`, `channels:history`). VERIFIED. Source: [Token types](https://api.slack.com/authentication/token-types), [Bot vs user tokens](https://slack.dev/two-keys-to-one-platform-understanding-bot-and-user-tokens/). Fetched 2026-09-20.
- Rate limits use separate buckets per "API method × workspace × app". For non-Marketplace apps, `conversations.history`/`conversations.replies` have been hard-limited to 1 request per minute / 15 objects per request for new installs since 2025-05, and from 2026-03-03 for existing installs as well (Marketplace-approved apps get 50+ requests per minute, with a maximum/default limit of 1000). Whether this restriction applies to apps used exclusively in a personal workspace (undistributed) is unclear — if the app is not listed in the Marketplace, it may be caught regardless of whether it is "commercially distributed". VERIFIED (the restriction itself) / UNVERIFIED (whether personal-only internal apps are exempt). Source: [Rate limits](https://docs.slack.dev/apis/web-api/rate-limits/), [Rate limit changes for non-Marketplace apps](https://api.slack.com/changelog/2025-05-terms-rate-limit-update-and-faq). Fetched 2026-09-20.
- Using multiple workspaces requires a separate OAuth installation per workspace (reusing the same app definition and installing it multiple times) — a "single install across multiple workspaces" is only possible via the Enterprise Grid org-wide install path. VERIFIED (inferred from the per-workspace bucket structure, cross-checked against the openclaw enterprise-grid doc). Source: the rate limits doc above + [openclaw docs/channels/slack/enterprise-grid.md] (repo listing, 2026-09-20).

**Gmail**
- `users.watch` connects the Gmail mailbox to a Cloud Pub/Sub topic and publishes a message containing only `emailAddress` + `historyId` (a watermark) on change — no message body arrives; the diff must then be fetched via `history.list`. **Channel expiry is 7 days**, so re-registration via daily cron is required. VERIFIED. Source: [Configure push notifications with the Gmail API](https://developers.google.com/workspace/gmail/api/guides/push), [users.watch quota 100 units](https://www.unipile.com/gmail-api-push-notifications/). Fetched 2026-09-20.
- Pub/Sub is a Google-operated message bus, so using a **pull subscription** requires no public HTTPS endpoint on our side at all (polling outbound from the Mac mini is all it takes) — a public endpoint is only needed when using a push subscription. This is the decisive difference from the Calendar API's webhook approach. VERIFIED (standard Pub/Sub architecture behavior). Source: [Gmail push guide](https://developers.google.com/workspace/gmail/api/guides/push). Fetched 2026-09-20.
- If the OAuth consent screen is in "Testing" status (= unverified app), the refresh token issued **expires after exactly 7 days**. Publishing to "Production" removes this restriction. Even a single-person personal app must re-authenticate every week if it stays in Testing. VERIFIED. Source: [Google OAuth Refresh Token 7-day limit](https://www.unipile.com/google-oauth-refresh-token/), Google's official OAuth2 refresh-token-expiration doc (cited by the page above). Fetched 2026-09-20.
- "Sensitive" scopes such as `gmail.modify` (read+compose+send) can keep being used without formal verification as long as there are **fewer than 100 test users** (registered as test users in the Cloud Console); verification is required once you exceed 100 or make the app public. "Restricted"-tier scopes (whole-mailbox-export level) are separately stricter. A personal-only project (one user = yourself) has effectively almost no verification burden — but you must still publish to Production so the refresh token doesn't die (verification and publishing are separate procedures). VERIFIED. Source: [Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [Nylas — Google OAuth app verification](https://www.nylas.com/blog/google-oauth-app-verification/). Fetched 2026-09-20.
- Gmail API quota for new projects (created after 2026-05-01): 1.2 million units per minute per project, 6,000 units per minute per user. `messages.send` costs 100 units per request → up to 60 messages per minute per user. `users.watch` costs 100 units/call. VERIFIED. Source: [Gmail API usage limits](https://developers.google.com/workspace/gmail/api/reference/quota), [Unipile — Gmail API limits 2026](https://www.unipile.com/gmail-api-limits/). Fetched 2026-09-20.
- The Hermes Agent's (always-on on the Mac mini) email gateway is IMAP/SMTP-based and **reply-only** (replies on outbound threads only; not new sends, not real-time push) — this comes from internal project records (a past Hermes analysis), not from this session's web verification. UNVERIFIED (not re-verified in this session; needs a code check).

**Outlook / Microsoft 365 (personal + work)**
- Graph change notifications (webhooks) require a **public HTTPS endpoint** — delivery to private/localhost does not work. Verification is a handshake that echoes back the `validationToken` when the subscription is created, and unlike Google Calendar it does not require Search Console domain-ownership verification (not stated in the docs). VERIFIED (endpoint requirement) / relatively low confidence (no domain verification needed — proving a negative, so not fully VERIFIED; MEDIUM). Source: [Receive change notifications through webhooks](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks), [Change notifications overview](https://learn.microsoft.com/en-us/graph/outlook-change-notifications-overview). Fetched 2026-09-20.
- The **maximum lifetime of a mail resource subscription is 4230 minutes (≈2.94 days)**; setting less than 45 minutes is automatically corrected to 45 minutes. If you don't renew (`PATCH` expirationDateTime) before expiry, you must create a new one. VERIFIED. Source: [subscription resource type](https://learn.microsoft.com/en-us/graph/api/resources/subscription), [Elio Struyf — renewing Graph webhook subscriptions](https://www.eliostruyf.com/creating-and-renewing-your-microsoft-graph-webhook-subscriptions/). Fetched 2026-09-20.
- Selecting "Accounts in any organizational directory and personal Microsoft accounts" in the app registration (Entra ID/Azure AD) lets you handle **personal Outlook.com accounts and work (M365) accounts with a single app registration** (the `/common` authority endpoint). IMAP/POP/SMTP are also supported via OAuth2, but Microsoft recommends the Graph API for functional advantages such as webhooks. VERIFIED. Source: [Unipile — Microsoft Graph OAuth email](https://www.unipile.com/microsoft-graph-oauth-email/), [Authenticate IMAP/POP/SMTP via OAuth](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth). Fetched 2026-09-20.
- Publisher verification (the blue verified badge) is a procedure for **multitenant distribution apps** and is not enforced for single-person personal use (single tenant / personal account; only an "Unverified" warning appears and it works once you consent yourself) — for a personal project used only by you, it can practically be skipped. VERIFIED (the procedure's purpose) / MEDIUM confidence that the personal-use exception applies. Source: [Publisher verification overview](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview). Fetched 2026-09-20.

**Google Calendar**
- The `events.watch` channel likewise **expires after 7 days** and has no auto-renew mechanism, so you must manually open a new channel and swap it in before expiry (the expiry time arrives in the `X-Goog-Channel-Expiration` header of every notification). VERIFIED. Source: [Google Calendar push notifications](https://developers.google.com/workspace/calendar/api/guides/push). Fetched 2026-09-20.
- Receiving Calendar push requires **verifying ownership of the callback domain via Search Console** and registering it in the API Console — unlike Gmail's Pub/Sub approach, it needs a genuine "domain you own + valid SSL". `*.ts.net` (the subdomain Tailscale Funnel provides) is a Tailscale-owned domain, so an individual cannot easily prove ownership in Search Console → in practice, Calendar push is blocked in a personal setup. VERIFIED (the requirement) / the likelihood of Funnel domain verification failing is an inference (MEDIUM; needs re-confirmation by actually trying it). Source: [Verifying domains for push notifications](https://support.google.com/googleapi/answer/7072069), [Google Calendar push guide](https://developers.google.com/workspace/calendar/api/guides/push). Fetched 2026-09-20.
- Without your own domain, the alternative is **polling**: incrementally call `events.list` with a `syncToken` (receiving only changes); a short interval (e.g. 1–5 minutes) feels real-time enough. UNVERIFIED (quota consumption for specific polling intervals is unverified, though `events.list` is generally known to be cheap under the standard read quota).

## 3. Options / comparison

|Channel | Real-time strategy options | Chosen candidate | Rationale |
|---|---|---|---|
| Slack | Socket Mode (WS) vs Events API (HTTP, requires a public endpoint) vs RTM (unavailable to new apps) | **Socket Mode** | Only an outbound connection from the Mac mini needs to be open; no public IP/domain/TLS required; the official RTM replacement path |
| Slack token | Bot (xoxb) only vs Bot+User (xoxp) | **Both Bot+User** | "Everything that reaches me" requires search / other-people's-DM visibility that a bot cannot cover, and "send as myself" requires a user token |
| Gmail | watch()+Pub/Sub push vs history.list polling vs IMAP IDLE | **watch()+Pub/Sub pull subscription** | No public endpoint needed (the Mac mini only has to poll), sub-second latency, quota savings. IMAP IDLE is OAuth2-supported but cannot use Gmail's native label/thread model |
| Outlook notifications | Graph webhook (requires public HTTPS) vs delta query polling | **Near term: delta polling / Mid term: Graph webhook + Tailscale Funnel** | Webhooks need renewal every 4230 minutes, and polling is cheaper and simpler until Funnel stability is verified |
| Outlook protocol | Graph API vs IMAP+OAuth2 | **Graph API** | Feature advantages including webhooks, delta, categories, and conversation threads; Microsoft's official recommendation |
| Calendar notifications | events.watch (requires domain verification) vs syncToken polling | **syncToken polling (1–5 minute interval)** | A Funnel domain is likely unable to pass Search Console ownership verification; calendars lack the sub-second urgency of email/Slack, so polling is sufficient |

## 4. Recommendation for omnis

**Slack** — Socket Mode + a separate app installation per workspace (including a user token); fork openclaw's manifest as-is and just trim the scopes. Effort: **S** (a reference manifest exists). Risk: installing a personal app may be blocked in a company workspace that requires admin approval (ToS/organizational-policy risk, MEDIUM) — "acting as your own account" with a user token is not a problem under Slack's ToS (a normal OAuth flow delegated by a person).

**Gmail** — watch()+Pub/Sub pull, and be sure to publish OAuth as "Production" (verification itself can be skipped, since this is personal use with fewer than 100 users) to avoid the 7-day expiry. Effort: **M** (Pub/Sub topic/subscription setup, daily re-watch cron). Risk: low (almost no account-suspension risk; normal use of official APIs).

**Outlook** — start phase 1 with delta query polling (minimal setup friction), then experiment with Graph webhook + Tailscale Funnel once it stabilizes. Personal accounts don't require publisher verification, so the barrier to entry is low. Effort: **S→M**. Risk: low, but Funnel stability is unverified (URL stability across Mac mini reboots / network changes needs to be confirmed).

**Google Calendar** — defer push; syncToken polling alone for the MVP. Effort: **S**. Risk: low.

**Shared infrastructure** — strongly recommend self-hosting an open-source OAuth broker like Nango rather than implementing one yourself (hand-rolling token refresh/storage for 4+ OAuth providers on a one-person project is a waste). Large effort savings.

## 5. What to borrow

- **`github.com/openclaw/openclaw` — `extensions/slack/`, `extensions/imap/`, `extensions/google/`**: borrow the per-channel independent plugin package structure as-is for omnis's "adapter per channel" architecture. Copy the Socket Mode manifest (JSON) and scope list from `docs/channels/slack/setup.md` as a starting point.
- **The "Gateway" concept in `docs/channels/index.md`**: every channel connects through a single Gateway, and status is managed with CLIs like `openclaw channels add`/`channels status --probe` — apply the same "channels add/status" CLI pattern to omnis's Mac mini hub daemon.
- **`extensions/imap/`**: Outlook/Gmail IMAP fallback adapter code already exists, so it can be referenced directly as a fallback path if Graph webhooks prove unstable.
- **Nango (`NangoHQ/nango`)**: consider self-hosting OAuth token storage/refresh/multitenant credential management and layering it in as omnis's own OAuth broker. Using just the Auth/Proxy two primitives is enough (Functions may be unnecessary).
- **The Pub/Sub pull-subscription pattern**: reflect in the design the asymmetry that only Gmail can be real-time without a public endpoint — even with the Mac mini staying an "outbound-only" poller, Gmail is genuinely real-time, and Slack via Socket Mode is likewise real-time while remaining outbound-only. Reflect in the onboarding UX that only Outlook/Calendar require a polling-interval compromise (label these channels to the user as "near real-time").

### Corrected recommendation

**Google Calendar**: Do not default to "push is blocked, use polling only." The brief's own cited reason — that a `*.ts.net` Tailscale Funnel domain can't pass Search-Console domain-ownership verification — is based on a Google requirement that Google's own support docs say no longer exists ("domain verification in the API Console is no longer required"). The current, documented requirement for `events.watch` push is just an HTTPS endpoint with a valid, non-self-signed, non-expired SSL certificate — which Tailscale Funnel provides out of the box via Let's Encrypt. Recommended change: run a real spike (create an `events.watch` channel pointed at the Mac mini's Funnel URL) before committing to syncToken-only polling. If the Funnel endpoint validates, Calendar can join Gmail and Slack as a genuinely real-time, outbound-only channel; polling should be the fallback, not the primary plan, and the "Calendar is second-class / can't be real-time" framing in the onboarding-UX note (§5) should be softened pending that test. Separately, the Outlook webhook renewal cadence in §3/§4 can be relaxed from "~every 3 days" to "up to weekly" per the corrected 10,080-minute Graph mail-subscription limit (row 6), lowering the operational cost of choosing Graph webhooks over delta-query polling for Outlook.
