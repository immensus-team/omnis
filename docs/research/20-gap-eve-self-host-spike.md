# GAP 1 — Eve self-hosting: re-opening the harness decision

Fetched/spiked 2026-09-20.

## 1. TL;DR

`11-agent-harness.md` rejected Vercel Eve on a single ground — that "it assumes Vercel Functions deployment and therefore pairs poorly with an always-on Mac mini" — but that premise is **wrong**. Confirmed via eve.dev's official docs and an actual spike (running `eve build && eve start` on top of local Postgres): eve self-hosts as a pure Node/Nitro server, a real package named `@workflow/world-postgres` persists state durably into local Postgres, and cron is driven by Nitro's own scheduler. With the Slack channel (env-var mode), an approval-gated tool, a schedule, and the postgres world all in place, build, startup, and healthcheck all succeeded, and idle RSS was ~550MB across the two processes combined. But whether to adopt it as the kernel is a separate question — eve is not an event bus; it is "agent directory = separate Node server + separate Postgres schema," so turning all 5–10 capabilities omnis needs into Eve agents would multiply the process count against a 16GB budget. Conclusion: build the kernel by hand on Postgres as 11 originally proposed, and adopt Eve only for the 1–2 individual agents that need approval + schedule + channel together (reply drafting, nightly digest, and the like).

## 2. Facts

- **VERIFIED** — eve.dev's official deployment docs explicitly support self-hosting: "For self-managed infrastructure, eve compiles to a standard Nitro server under `.output/` that runs as a Node service... Choose this when you operate your own Node or container infrastructure." Source: [eve.dev/docs/deployment](https://eve.dev/docs/deployment), accessed 2026-09-20.
- **VERIFIED** — the self-hosting procedure is `eve build` followed by `PORT=3000 eve start --host 0.0.0.0`, and "Run this process under the same process manager or container platform you use for other Node web services." Source: [eve.dev/docs/deployment/self-hosting](https://eve.dev/docs/deployment/self-hosting), accessed 2026-09-20.
- **VERIFIED** — the default Workflow world stores execution state on disk under `.eve/.workflow-data`, and `agent.ts` can specify an installed world package (e.g. `@workflow/world-postgres`) via `experimental.workflow.world`. Source: same as above + `node_modules/eve/docs/concepts/execution-model-and-durability.mdx` (confirmed directly by the spike).
- **VERIFIED** — two paths a reverse proxy must forward when self-hosting: `/eve/` (health, sessions, streams, channels, tools, subagents) and `/.well-known/workflow/` (workflow callbacks). "A proxy restricted to `/eve/` lets a session start, but the run stalls when its callback can't reach eve." Source: self-hosting doc, 2026-09-20.
- **VERIFIED** — Nitro's schedule runner starts automatically on the `eve build && eve start` path ("The standard `eve build && eve start` path starts Nitro's schedule runner"); there is an explicit warning that switching to a custom HTTP-only preset leaves cron registered but never actually running. Source: self-hosting doc + `node_modules/eve/docs/schedules.mdx`, "Self-deployed hosts" section.
- **VERIFIED** — explicit warning about production authentication: "Don't rely on `vercelOidc()` as the only production authenticator outside Vercel." Source: self-hosting doc, 2026-09-20.
- **VERIFIED (confirmed directly by the spike)** — `@workflow/world-postgres` (npm, latest `5.0.0-beta.44`, protocol-compatible with the `@workflow/*` "5.0.0-beta" line that eve 0.63.0 requires) is real and connects via the `WORKFLOW_POSTGRES_URL` or `DATABASE_URL` environment variable. It runs on Graphile Worker (queue) + Drizzle ORM + `pg`. Source: `npm view @workflow/world-postgres`, package README, 2026-09-20.
- **VERIFIED (confirmed directly by the spike; a gotcha absent from the docs)** — self-hosting.md only tells you to "choose" a world package and stops there, but in practice you must first run the schema migration with `npx --package=@workflow/world-postgres bootstrap`. Without it, `eve start` dies immediately with `relation "workflow.workflow_runs" does not exist` (reproduced and resolved in the spike). Tables created: `workflow_runs`, `workflow_events`, `workflow_steps`, `workflow_hooks`, `workflow_stream_chunks`, `workflow_waits`, `workflow_event_slots` (under the `workflow` schema).
- **VERIFIED (confirmed directly by the spike)** — `npx eve@latest init` on `eve@0.63.0` **requires Node ≥24** (`engines.node: "24.x"` in `package.json`; running on Node 22 fails immediately with `eve requires Node.js >=24`). The Mac mini's actual Node version was not checked in this session (the spike ran on a MacBook Pro, where both Node 22 and 24 are installed via brew, so we switched to 24 to proceed).
- **VERIFIED (confirmed directly by the spike)** — with a Slack channel, a custom tool gated by `always()` approval, a cron schedule (`defineSchedule`), and `@workflow/world-postgres` all in place, `eve build` succeeded (12MB output / 2.71MB gzip, `node_modules` 168MB). The Slack channel also compiles without Vercel Connect, using the env-var approach (`SLACK_BOT_TOKEN`) — confirming at the code level that Vercel Connect is not required for self-hosting.
- **VERIFIED (confirmed directly by the spike)** — `eve start` stayed alive as an independent background Node process unrelated to the coding-agent session (launched detached with `nohup`, and it kept responding across several subsequent separate commands). `GET /eve/v1/health` → `{"ok":true,"status":"ready","workflowId":"workflow//eve//workflowEntry"}` (HTTP 200).
- **VERIFIED (confirmed directly by the spike)** — production builds reject unauthenticated requests by default: calling `POST /eve/v1/session` without a token returns `401 {"code":"unauthorized","error":"Authorization is required for this route."}` — confirming that self-hosting.md's "replace `placeholderAuth()` with production authentication" warning is actually enforced.
- **VERIFIED (confirmed directly by the spike)** — the schedule (`agent/schedules/heartbeat.ts`) was compiled at build time into a separate Nitro scheduled-task module, `.output/server/_virtual/eve.schedule.mjs` (which calls `dispatchScheduleTask`) — confirming the docs' "Nitro's schedule runner" claim at the level of the actual build artifact.
- **VERIFIED (confirmed directly by the spike)** — memory at idle (no traffic, no sessions): the `eve start` CLI wrapper process RSS ≈303MB, its child, the actual build server (`.output/server/index.mjs`), RSS ≈250MB, ≈550MB combined. Graphile Worker logged a `maxPoolSize(10) < concurrency(50)` warning (both are defaults — needs tuning before production). **The measurement environment was a 64GB MacBook Pro, not an actual 16GB Mac mini** — this is a reference figure, not a confirmed one.
- **VERIFIED** — the `vercel/eve` repository: 5,270★, Apache-2.0, `pushed_at: 2026-09-19` (one day earlier, active), 857 open issues. Source: `gh api repos/vercel/eve`, 2026-09-20.

## 3. Options / Comparison

| | Vercel Eve (self-host) | 11's hand-built kernel (Postgres events + LISTEN/NOTIFY + node-cron + pending_approvals) |
|---|---|---|
| Deployment shape | Pure Node/Nitro server (`eve build && eve start`), no Vercel needed | Already designed that way (always self-hosted) |
| State storage | `@workflow/world-postgres` — can attach to the existing local Postgres (confirmed by the spike) | Already the same Postgres |
| Approval gate | Built in. `never/once/always/auto()` + custom policy functions, request/response authorization split, durable pause (survives process restarts) | Must be designed and implemented by hand (`pending_approvals` table + polling) |
| Schedule | Built in (`defineSchedule`, started automatically by Nitro's schedule runner) | `node-cron` wired by hand |
| Channel adapters | Slack/Discord/Telegram/Teams/Twilio/GitHub/Linear/MCP and more provided out of the box (renders approvals as native buttons) | Implemented by hand per channel (KakaoTalk isn't in Eve either, anyway) |
| Process model | **1 agent = 1 Node server + 1 port + (1 schema unless worlds are shared)** | 1 event bus handles many capabilities — process count does not grow |
| Maturity / drift risk | 3 months in public, the `@workflow/*` protocol is pinned to a "5.0.0-beta" line and mismatched versions are rejected at runtime — breaking changes are possible | Zero risk (our own code), 100% of maintenance falls on us |
| Node version requirement | ≥24 (confirmed by the spike) | None (fits the current stack) |
| Fit for a 16GB budget | ~550MB idle per agent (fine-grained measurement, MacBook-based) — **N× if you adopt N of them** | 1 process covers the entire kernel |
| omnis's "agent session = inbox thread" requirement | None — Eve's subagent/remote-agent is delegation between its own agents, not an adapter that folds external Claude Code/Codex CLI sessions in as channels (the `subagents/` and `remote-agents.md` docs were not read in this pass) | Must be built by hand regardless, separately from the kernel — orthogonal |

## 4. Recommendation for omnis

**Discard 11's rationale that "Eve is rejected on deployment-shape grounds" — it is not true.** eve.dev's primary docs and an actual build + startup + healthcheck spike confirmed that Eve runs as a pure Node process on an always-on Mac mini and leaves durable state in local Postgres. Risk: low (for this specific claim only).

**Even so, do not adopt Eve as omnis's "kernel."** The reason is not deployment shape but **unit of architecture**: Eve's unit is "agent directory = separate Node server process + (unless worlds are shared) separate Postgres schema." What omnis needs is the opposite — a kernel where "one event bus handles many channels/capabilities." Building all 5–10 capabilities — reply drafting, nightly digest, labeling, CRM follow-ups, and so on — as separate Eve agents would grow the Node process count to 5–10 against a 16GB budget, which directly conflicts with `18-mac-mini-hub-ops.md`'s "don't add one more VM/process" recommendation. Effort: this conclusion is a re-confirmation only, no additional work (S), Risk: low (strategic decision).

**Adopt Eve only for the 1–2 "individual agents that need approval + schedule + channel together."** Concretely: a context-aware reply-drafting agent, or a nightly archive-digest agent. Both have exactly the shape Eve handles well: "wake on cron → wait for human approval → send to a channel." For the world, don't let each agent create its own schema; instead use the "share an existing `pg.Pool`" option from the README (`createWorld({ pool })`), or at minimum unify on a single `WORKFLOW_POSTGRES_URL` so there is only one schema. Effort: S (half a day per agent based on the spike), Risk: no ToS issue (Apache-2.0), maintenance risk medium (beta protocol pin; pin `eve`/`@workflow/*` versions and upgrade only deliberately).

**The kernel itself (event bus + scheduler + approval gate) should still be built by hand on Postgres as 11 originally proposed — that conclusion stands.** Just swap the rationale from "because Eve is Vercel-only" to "because Eve's per-agent process unit doesn't fit omnis's many-capabilities-single-hub requirement." Effort: M (same as the existing estimate), Risk: maintenance (on us) — unchanged.

**Record the Node ≥24 requirement as an execution precondition.** If the Mac mini's current Node version is below 24, then the moment you use Eve — whether for a spike or for the real 1–2 agents — upgrading is a prerequisite task. If you move on without checking, you will be blocked immediately at the first `npx eve init`.

## 5. What to borrow

- **Approval policy API design** (`eve/tools/approval`: `never()/once()/always()/auto()` + custom policy functions, the `session.auth.current` vs `session.auth.initiator` distinction, and the pattern of separating request from response to check "who is authorized to approve this particular call" independently) — port the **state machine design**, not the code, into 11's `pending_approvals` table as-is. Pointer: `node_modules/eve/docs/tools/human-in-the-loop.md` (spike artifact) or https://eve.dev/docs/tools/human-in-the-loop.
- **`defineSchedule`'s markdown-vs-run dichotomy** (fire-and-forget prompt vs a full handler controlled with `to(channel).send()` + `waitUntil()`) — a clean API shape worth applying as-is to the omnis scheduler we will build by hand with node-cron. Pointer: https://eve.dev/docs/schedules, `node_modules/eve/docs/schedules.mdx`.
- **`@workflow/world-postgres`'s schema design** (`workflow_runs/events/steps/hooks/stream_chunks/waits/event_slots`) — a far more proven "queue + steps + hooks + streams" separation model than the single "events table" that 11's kernel currently lumps everything into. Pointer: the "Database schema" section of the npm `@workflow/world-postgres` README, or the `workflow.*` tables actually created in this spike's `eve_spike` DB.
- **The channel adapter interface's name/concept list** (Slack/Discord/Telegram/Teams/Twilio/GitHub/Linear/MCP) — use only as a naming and feature-taxonomy reference when designing omnis's own channel plugin interface (Slack/KakaoTalk/Gmail/Outlook/Telegram/LinkedIn/WhatsApp) (the code is tied to Vercel Connect and cannot be taken as-is). Pointer: https://eve.dev/docs/channels/overview.
- **The `pg.Pool` sharing option** (`createWorld({ pool })`) — the concrete code pattern for when omnis later attaches only a specific slice of functionality to Eve: hand over the existing app's pool instead of opening a separate Postgres connection pool. Pointer: the "Programmatic usage" section of the `@workflow/world-postgres` README.

## 6. Open questions

- Whether the Mac mini's actual Node version is ≥24 is unconfirmed — this spike was run on a MacBook Pro (switched from Node 22 to 24). Needs checking.
- Why the `bootstrap` migration step for `@workflow/world-postgres` does not appear in the body of self-hosting.md (was it automated in a newer version, or is it simply a docs omission) — needs a search of the vercel/eve issue tracker.
- RSS under real traffic (concurrent sessions, accumulated conversation history) — this measurement is an idle, no-traffic, single-agent figure and is a directional reference only.
- Whether running `.output/server/index.mjs` directly with `node` instead of `npx eve start` saves the CLI wrapper process (~300MB) — unverified.
- What happens if an existing `eve start` process is serving live traffic while `eve build` is re-run (zero-downtime deploy or not) — unverified.
- Whether Eve's subagents/remote-agents feature (`docs/subagents/`, `docs/guides/remote-agents.md`, not read in this pass) can be used at all to "fold existing Claude Code/Codex CLI sessions in as channels," or whether that part must be 100% self-implemented regardless of the harness choice.
